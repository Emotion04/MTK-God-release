# 文档维护

文档帮助下一次开发作判断：保留非显然的限制、重要取舍、可复查的设备结论。
实现步骤和参数能从代码直接看出时，链接源码即可。
当前说明先写结论、适用条件和操作入口；原因只保留会影响后续选择、兼容或排障的部分。
通常用一句说明非显然的取舍，复杂依据链接实验或参考页；迁移经过和交付统计留在任务记录中。

## 内容放在哪里

| 内容 | 位置 |
|---|---|
| 开发契约、UI 与文案 | `dev/architecture.md`、`ui.md`、`wording.md` |
| 设备能力、兼容差异、重要发现 | 对应主题 `facts.md`；命令、协议和配置细节放其参考页 |
| 仍决定要做的工作 | [dev/todo.md](dev/todo.md) |
| 值得复用的实验条件和结果 | [experiments/](experiments/README.md) |
| 固定版本的外部实现摘录 | [reference/](reference/README.md) |
| 已被替代但仍有排障、回归或决策价值的记录 | [archive/](archive/README.md) |

先搜索功能名、问题关键词或已有事实 ID，更新原位置。新增长文档时在最近的目录入口加链接。
结论影响其他主题时，在对方入口加交叉链接；同一结论只维护一份。
已有事实 ID 保持稳定；普通段落无需为了格式分配 ID。

## 如何写一段当前说明

先明确下一位读者要用这段内容作什么决定，再按需要写：**当前结论 → 适用条件 → 必要原因或依据 → 操作入口**。
这是信息顺序，不是必须填满的模板；简单契约可以只有一句，复杂证据链接到原记录。

例如：

> CPU 请求由 `CpuControl` 串行协调。释放失败时保留旧句柄并停止应用，
> 避免新旧请求合并改变目标区间；协议依据见 [CPU 协议](cpu/protocol.md)。

这段同时提供职责、失败处理和必要原因。原因值得保留，是因为它会改变实现顺序；
如果删掉一句仍不影响读者理解条件、选择方案或处理风险，就可以删掉。
更新时重写受影响段落，使全文描述当前状态；读者应能直接得到结论，而无需沿着澄清和修正记录推导。
交付前从新读者视角检查：能否找到唯一当前说明、知道其适用范围，并找到需要继续核实的依据。

## 协作分工与顺序

协作修改文档体系时，先定稿受影响的规范，再按规范更新内容。
日常开发直接使用现有规范，同次更新相关说明。

并行协作时按文件分配维护者，以下是文档重构的分工参考：

| 归属 | 文件 |
|---|---|
| 规范维护 | `docs/dev/**`、`README.md`、`mtk-optimizer/README.md`、`docs/README.md`、`docs/CONTRIBUTING.md`、`AGENTS.md`、`tools/**` |
| 内容维护 | `docs/cpu/**`、`docs/thermal/**`、`docs/device/**`、`docs/tools/**`、`docs/reference/**`、`docs/experiments/**`、`docs/archive/**` |
| 共同边界 | `docs/dev/wording.md` 与 `tools/check_strings.py`；修改 `feature/**` 的用户文案时同时核对两边 |

并行修改期间，同一文件由一位维护者编辑，交接时说明已改文件和结论。
独立开发按任务更新受影响文件；`wording.md` 与文案检查器的职责变更一起核对。
跨模块稳定契约放在 `dev/architecture.md`，仓库级工作入口放在 `AGENTS.md`。

## 核心功能与文档类型

不为每个功能、页面或类建立一份说明。只有当内容包含跨模块契约、兼容范围、恢复规则、
非显然的设备限制，或代码本身不能表达的长期取舍时，才增加或扩展文档。
简单功能的实现、字段和调用关系以源码与测试为准，不复制到文档中。

本项目按问题组织，而不是强行按四种文档类型拆目录：`dev/` 负责开发指南与架构解释，
主题目录负责当前事实和参考资料，`experiments/` 只保存可复用的验证，`archive/` 只保存仍有追溯价值的旧材料。
只有影响多个模块、需要长期保留且不适合放入当前架构页的取舍，才单独记录决定；记录决定日期、
状态（如 accepted、superseded 或 deprecated）、适用范围和替代关系。普通当前说明不加文件日期或文档版本号。
规范保留项目目标、稳定契约和可复用判断。一次错误也可能值得记录，但判断标准是它的
长期价值，不是出现次数：涉及数据丢失、权限边界、设备状态恢复或安全的错误；包含源码
无法推出的原因、取舍或验证边界；或者重新发现代价很高的事实，应压缩成一条事实、契约
或排障经验。只影响当前实现的拼写、临时操作失误和从代码即可看出的错误，修正后不留规则。

判断是否正在重复时，先搜索同一症状、同一错误归因或同一修复动作，而不是只搜索相同措辞。
两次独立任务遇到同类问题、交接时再次发生，或多个 Agent 都需要同一澄清，才是明显的复发信号；
单次高代价事件无需等待第二次。新规则应优先补充已有原则，写成适用于问题类别的判断，
不要写成针对某个模型、某次对话或某个表面例子的禁令。维护章节时合并重复规则，并删除已无适用范围的规则。

复杂或需交接的任务可以在任务工作区或交付说明中使用简短实现笔记，记录关键选择及原因、验证结果和未解决问题。
笔记用于当前任务，收尾时将长期结论归并到现有说明，已决定继续的工作进入 `todo.md`；
剩余过程记录按追溯价值删除或归档。普通小修改使用交付说明即可。

## 每次变更的收尾

在同一次交付中检查受影响的说明、待办和引用；如果源码、证据和当前文档已经一致，
不为了满足流程新增说明：

1. 当前说明直接改成最终结论，删除被澄清或被替代的说法。
2. 待办完成、取消或被新方案替代时，从 `todo.md` 删除；代码完成与设备效果验证分别判断。
3. 重要原因压缩成一句取舍或排障经验；只是过程、重复内容或失效路径，删除。
4. 只有独有证据或重要历史原因值得追溯时才归档，并写明当前入口；修正原链接。

例如最终把功能移到新位置，当前文档只说明新位置。旧位置只有能解释兼容处理或回归风险时才留下。

文档进入版本控制以保留可恢复的修改历史。
删除或大改文档前，先检查它是否在 `HEAD` 或已有备份中，并确认独有信息已经迁移；
最终提交由用户审查决定，检查脚本不负责提交，也不把未提交状态当成内容错误。

## 来源、日期与兼容范围

设备结论旁边简写依据：测量日期、机型/ROM、执行身份和影响结果的条件，附原始文件、报告或命令入口。
范围重复时引用 [VERSIONS.md](VERSIONS.md) 的基线。代码契约链接实现；共享原始资料位置见 [SOURCES.md](SOURCES.md)。

日期用于说明证据发生在什么时候。普通指南靠代码变更同步维护；
实验记录用实验日期，兼容结论用适用的 ROM 或 App 版本，不给每份文件另加维护日期或文档版本号。
文档是否被修改看 Git 的提交记录、`git diff` 或 `git blame`；不要用文件系统的修改时间推断事实是否更新。

比较新旧结果时先看条件：同一问题、可比条件下采用最新有效核验；
不同机型、ROM、身份或运行状态下的结果分列必要差异。
配置存在、命令接受和场景效果是不同观察；测不到的部分说明边界。
旧测试的一次失败不能推出所有环境都失败。

**会变的量写成取值集合，不写单次读数。** 由策略、场景、温度或前台应用决定的量
（HAL SKIN 阈值、当前频率上限都是）本来就会变。写成“本次读到 X”会被下一次
当成结论直接复用，然后对不上。正确的写法是 **可能的取值 + 各自在什么条件下出现**，
并写明“相符或不符都不能唯一指认”。单次读数只是取证条件，不是结论。
“最近一次”只有在前置条件可比且完整记录时才有意义，不能用孤立的新读数覆盖取值集合。

系统升级后按 [VERSIONS.md](VERSIONS.md) 更新基线及受影响事实，
只有确实需要并行维护的差异才保留旧分支。

## 待办和实验的尺度

`todo.md` 只列已经决定推进的工作，写清问题、完成判据，必要时附阻塞条件或相关入口。
尚未决定的想法留在当前任务讨论中，决定推进后再转成待办；不要让 Agent 把想法当成任务。
能力限制、尚未观测的效果和移植设想写在相关说明中。

**测量结果和实现细节不是一回事，判定尺度也不同。** 实现细节能从代码看出来，删了不心疼；
测量结果跑一遍才有，代码里没有，删掉就要重测。**决定"该不该保留"时用这条尺子，
不要用"能不能从代码推出来"** —— 后者会把测量结果一起裁掉，而它们正是最贵的部分。
典型例子：某组开关的实际取值与往返、各档位的实测结论、某条命令在本机的真实行为。

恢复被裁掉的测量时，先定位原始报告、实验记录或可复查入口；没有独有证据就不按记忆补写。
有证据时只保留结论、测量日期、机型/ROM、关键条件、边界和入口，合并进已有事实或实验页，
不复制源码已有的命令目录，也不把多轮过程扩成流水账。

小测试只补强既有结论时，更新原条目的依据即可。
只有改变实现或兼容判断、提供可复用验证方法、或能避免重复走弯路的测试，才保留独立实验。
同一问题的多轮测试合并；[模板](experiments/TEMPLATE.md) 可删减。

## 检查

`python tools/check_docs.py` 检查本地链接、锚点、总索引可达性、显式待办的位置，
以及**文档反引号里点名的代码标识符是否真的存在**。最后一条防的是一类没人会去核的漂移：
文档写“子页按 SubScreen 的布局处理”，而代码里叫 `SubScreenScaffold`；
改名之后没人回头改文档，久了文档里的类型名就全是假的。
（举错名时用引号、别用反引号 —— 反引号是在**点名一个符号**，脚本会当真去查。）
通篇讲外部材料的页面（厂商配置里的应用名、第三方模块的类名）在开头写
`<!-- external-symbols -->` 声明，脚本会跳过它。**只有整页都在讲外部材料时才用** ——
一页主体讲本项目协议、只在一句里引用厂商服务名，那叫混合页，不该靠整页豁免
把本项目符号的漂移一起放过：把那处名称改用引号或换个说法即可。

它不判断任务是否已完成、事实是否正确或内容是否重复 —— 那三件事只能靠人对照源码和证据。
文案变更按 [wording.md](dev/wording.md) 检查。

交付前还需对照本次源码或证据确认：当前说明已替换旧说法，任务已收尾，相关主题能找到结论。
