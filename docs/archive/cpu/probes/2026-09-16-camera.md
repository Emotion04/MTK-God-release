# 0.3.12 相机只读对照

原始证据：[日志](../../evidence/2026-09-16_185221-v0.3.12-camera-readonly.txt)，
SHA256：A100270FFF7A2D9D3085100294668B1153FDEC29DDF26BD70D564634A5239D8B。
采集完整结束（`CAMERA_PROBE_COMPLETE`、`CAMERA_PROBE_EXIT=0`），但未严格按 20 秒操作，
因此按实际时间和读回状态分析，不按 planned_phase 直接判定相机状态。

## 观察到的事实

- 0–9 秒：policy7 为 600–2300，当前多为 600；policy4 为 550–2400。
- 11–15 秒：系统短暂把 policy7 下限抬到 2000、上限 2300；随后出现
  policy4=2850–2850、policy7=3400–3400，当前频率 3400。
- 18–38 秒：policy7 上限维持 3250，但上下限多次切换；当前频率在 0.6–3.25 GHz 间变化。
- 40 秒：policy4=2500–2850、policy7=2400–3250；当前 2.4 GHz。
- 43–45 秒：上限仍为 3250，45 秒当前频率为 3250；47–49 秒才回到 policy4 上限 2400、policy7 上限 2300。
- 51–58 秒：policy7 上限进一步降到 2100，当前多为 600。

因此，本次确实捕捉到系统状态允许 policy7 达到 3.25/3.4 GHz，也捕捉到上下限不是固定值。
但高频出现时没有可证明的相机服务状态：三个快照中的 power、media.camera 正文均因
`printf: Argument list too long` 丢失；thermalservice 有内容，PowerHAL dump 为空。
不能据此断言“打开相机解锁”，也不能断言温控是唯一原因。此处没有下发应用范围请求，
系统上下限变宽不证明本应用已能控制动态范围。

thermalservice 在 18:52:41 读到 CPU 约 88°C、总体 thermal status 0，TPU/SOC 的单传感器
status=3；18:53:01 总体 status=1，skin 约 41°C/status 1、CPU 约 82°C。
总体状态不能替代各传感器状态，亦不能据此解释全部上下限切换。

结论：日志有价值，证明“系统偶尔放开更高端点”的动态现象；尚不能定位触发者。
后续以 0.3.13 的限时流式采集替换此版，见 cpu-probe-guide.md；不要继续安装旧修正版。
