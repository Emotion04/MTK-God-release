# 0.3.13 连续拍照：场景上限变化证据

原始日志：[2026-09-16 20:22:34](../../evidence/2026-09-16_202234-v0.3.13-camera-burst-readonly.txt)。
用户说明：连续拍照延长高频；只读测试没有本应用频率请求。时间以 elapsed 为主。

## 可用性

60.006 秒完成，27 次频率采样、四轮服务快照；无预算丢弃。
相机/电源原始输出很大，首尾截取有明确标记，所需 Active Camera Clients 和近期事件在保留内容中。
SELF_CHECK 的 criticalNotFullyRead 表示整段未完整保留，不等于相机状态没抓到。
频率块标 DENIED 是 policy0 上下限拒绝读取；policy4/7 和 /proc/stat 仍有效。
PowerHAL 四次 dump 均为空；不能从空 dump 得出没有限制。

## 关键证据

| 相对时间 | 观察 |
| --- | --- |
| 0、15 秒相机快照 | Active Camera Clients=[] |
| 0–15.5 秒 | policy4 上限 2400、policy7 上限 2300 MHz |
| 19.9 秒 | policy4=2850–2850、policy7=3400–3400 |
| 22.6–27.3 秒 | policy7=600–3250，当前 3250；policy4 上限 2850 |
| 30 秒相机快照 | com.android.camera 活跃，新增 CONNECT 事件 |
| 31.7、34.2、37.2 秒 | policy7 依次为 2400–3250、3400–3400、2200–3250 |
| 45 秒相机快照 | com.android.camera 仍活跃；期间出现 DISCONNECT/CONNECT，不能按预设阶段认定已关闭 |
| 41.8–59.5 秒 | policy7 当前降至 600–1400，但上限仍 3250；policy4 上限仍 2850 |

事件日志内部时间与采集 wall 时间并非完全一致；只用快照内当前客户端和新增事件辅助关联，
不按事件秒数精确对齐 sysfs。采样为分次读取，不是原子快照。

热信息：30 秒快照总体 Thermal Status=0，但 HAL 实时 CPU=94.224°C/status=4，
GPU/NPU/TPU/SOC 也报 status=4；45 秒总体=1、CPU=73.707°C/status=0。
因此“总体状态为 0，所以没有热约束”不成立。热策略和性能场景可能同时变化，尚未识别仲裁顺序。

## 对实现的帮助与边界

结合此前普通计算满载仍被限制，本次支持“相机场景相关策略改变允许上限”的调查方向；
当前频率低而上限仍高，进一步区分了实际需求与允许区间。
这不是应用控制高频范围成功，也没有提供可直接复制的资源编号/参数。

服务列表确认当前 ROM 存在 `vendor.vivoperfservice`，可作为下一步只读定位目标，
但仅名称不能证明它负责上限。应先核对该 ROM 接口身份、可读配置及资源分发，
查找能合法改变范围上限的请求，而不是继续调整已验证的四个频率值或照抄相机整组 boost。
旧平台 thermal policy 数值不可当作当前 ROM 的协议；不猜 Binder 编号、不禁用温控。

这轮证据足够结束普通负载/相机关联确认，不要求用户重复同样拍照。
后续若需要设备补充，应一次集中提取相关接口/配置证据，先明确要验证的假设与读取范围。
目前未修改调频算法、未生成新 APK；稳定单值路径保留。
