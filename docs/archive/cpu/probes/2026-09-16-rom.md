## 当前固件中的具体线索

| 来源 | 已读到的定义 | 能得出的结论 |
| --- | --- | --- |
| nnapi_powerhal.json | PERF_RES_CPUFREQ_PERF_MODE / 0x00414000 / value=1 | 本机配置引用 CPU 性能模式；不是证明它解除上限 |
| powercontable.xml | PERF_RES_SCHED_DVFS_TRACKING / 0x1000c100 → /proc/sys/vivo_csc/dvfs_tracking_enable | Vivo 自有调度资源有真实编号与端点 |
| 同上 | ADAPTIVE_MARGIN / 0x1000c200；AM_CEILING / 0x1000c300，范围 716–1280 | 调度 margin 参数，不是 MHz 频率上限，禁止混为一谈 |
| 同上 | DYN_POLICY_MIN_ENABLE / 0x1000cd00，范围 0–3；RSC_QOS_LEVEL / 0x1000d000，范围 0–6 | 候选调度机制，尚未知各值具体语义及权限 |
| powerscntbl.xml | LAUNCH 等场景同时设置 CPU floor、DRAM、uclamp、CPUCORE_PERF_MODE 等 | 场景并非一个频率值；不能完整照搬来实现范围 |
| vperf/vperfmaps.xml | Vivo commonid/type → MTK hintid/timeout 映射 | 找到了本 ROM 的场景映射来源；描述符本身不提供方法签名或事务编号 |

上述均为保存下来的完整条目或完整片段，不将截断 XML 当完整文档解析。
资源表中的 `Compare=power` 不能按名称猜测仲裁规则；配置存在也不保证请求生效或允许 shell 调用。
`CPUCORE_PERF_MODE` 与 `CPUFREQ_PERF_MODE` 是不同资源，不能互换。
`FPSGO_THRM_ENABLE=0` 出现在部分场景，不代表关闭全部设备温控；不作为修复直接下发。

## 下一步决策

不再重复相机/满载采样。优先离线核对三份完整文件：
`/vendor/etc/powercontable.xml`（62207 字节）、`/vendor/etc/powerscntbl.xml`（58861 字节）、
`/vendor/etc/vperf/vperfmaps.xml`（38990 字节）。本轮实际证明它们可读。
当前采集器每文件仅保留 12000 字节，遗漏中段，不能确认完整相机场景和 CPU 资源分发。
这是报告保留策略的限制，不是用户操作或 Shizuku 读取失败。

后续实现应集中导出完整的定向配置（分块/文件流避免 Binder 上限），本地结构化解析
“相机场景 → MTK hint → 资源编号/节点/参数/恢复规则”，然后才选择单变量、有限时长实验。
尚未识别限制来源，未修改正式调频算法，也未证明无 root 能解除此上限。
