## 已确认的链路

`vperfmaps.xml:271–291` 中，相机 performance 场景使用 commonid `0x00001086`：

| type | 配置注释的用途 | MTK hint | timeout |
| --- | --- | --- | --- |
| 11 | 相机冷启动 | 1150 | 2000 ms |
| 12 | 相机包切换 | 1160 | 600 ms |
| 13 | 相机 Activity 切换 | 1161 | 600 ms |

最值得追踪的差异：普通应用冷启动 type=1 与相机 type=11 都映射 MTK hint=1150，但 `vivoResources` 中 `0xF0100000` 的值分别为 **9 和 71**。两者另有相同的 `0xF0040400=3`。这证明仅复制 MTK 场景不能保证复制相机路径；**71 的语义、接口和权限均未确定，不能解释为温控解锁编号，更不能当作 MTK 资源直接发送。**

`powerscntbl.xml:238` 的 1150 场景包含：

- 三簇 soft MIN：1800000 / 2850000 / 3250000 kHz；未设置 CPU MAX。
- `PERF_RES_THERMAL_POLICY=7`、`CPUCORE_PERF_MODE=1`、`FPS_FPSGO_THRM_ENABLE=0`。
- UCLAMP、DRAM、核心数及 Vivo 调度参数；主保持时间 6000 ms，附加 hint=30、保持 35000 ms。

3.25 GHz 与之前观测吻合，但这里是**启动下限请求**，不能用它直接解释采样中的持续上限，也未覆盖 3.4 GHz 连拍峰值。hint=30 没有以数字 30 的 scenario 出现在表中；本包无法确定其实现或运行时合并后的时长。

1160/1161（场景表第 334/356 行）使用 1500/2200/2200 MHz 下限及调度参数，没有显式 `THERMAL_POLICY`。名称为 `MTKPOWER_HINT_CAMERA_MODE` 的另一场景（第 204 行）主要配置 FPSGO/PID/CFP，没有 CPU MIN/MAX 或 `THERMAL_POLICY`。不要把这几个不同场景混为同一“相机解锁”。

## 排除误读

- 平衡启动 2150 也有 `THERMAL_POLICY=7`，同时明确要求 1400–1800 / 2000–2700 / 2200–2900 MHz（第 682 行）。因此值 7 本身不能称为“无上限”或“关闭温控”。
- 完整资源表没有定义 `THERMAL_POLICY`、常规 CPU MIN/MAX 的实现；场景仍引用它们。缺少 XML 定义不代表服务不支持，可能由内置分发处理，需要实现证据。
- `FPS_FBT_CEILING_ENABLE` 确有 ID `0x02064400`，路径 `/sys/kernel/fpsgo/fbt/enable_ceiling`，范围 0..1，Compare=more（资源表第 873 行）。配置中有设为 0 的场景，但若合并确按 more，另一个请求的 1 仍可能胜出；不能宣称发 0 就能解除限制。
- 未发现整组三簇 MAX=1800/2400/2300 的明确配置。2161 的 MAX 是 1800/2400/2400，数值接近不能证明它就是当前限制来源。
- 本包没有 Vivo 私有资源 `0xF0100000` 的实现，也没有服务的事务签名或调用者权限规则；静态配置不能证明 Shizuku 可调用。
