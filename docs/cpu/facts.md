## CPU-001 PowerHAL 协议与句柄

CPU 控制通过 `power_hal_mgr_service` acquire `0x16` / release `0x17`，
由 `CpuControl` 串行协调；释放失败时保留旧句柄。
协议、flags 和错误分支见 [protocol.md](protocol.md)，所有权见 [工程架构](../dev/architecture.md)。
依据：`CpuControl.kt`、`PerfLockController.kt`、`PowerHal.kt` 及协议页列出的一手实现。

## CPU-004 频率读回能力

2026-10-05 ADB shell 可读 `scaling_cur_freq`；三个 policy 的
`scaling_min_freq` / `scaling_max_freq` 为 `0660 system:system`，读回被拒。
shell 不在 system 组，DAC 已足以拒绝访问；相同 SELinux 标签不能排除其他策略限制。

采样峰值仅说明测试期间达到的频率，不等于真实上限。
`cpuinfo_max_freq` 是硬件报告范围，不能代替当前限制。
权限历史及开发影响见 [DEV-003](../device/facts.md#dev-003-cpu-频率节点可见性)。
依据：2026-10-05 本次 `ls -lZ`、`id`、`cat scaling_max_freq` 只读核验。

## CPU-006 热插拔与硬上限在本机的可用性

| 资源 | 已有观察 |
|---|---|
| 每簇核数 `0x00800000` / `0x00804000` | 2026-10-05 旧短时采样未看到热插拔；未证明这两项可控制核数 |
| 逐核上下线 `0x00810000 + 0x100×(核+1)` | 仅实验能力，效果未验证 |
| 逐核暂停调度 `0x0080C000 + 0x100×(核+1)` | 仅实验能力，效果未验证 |
| 硬上限 `0x0040C000` | 参考后端依赖的 `/proc/ppm/policy/hard_userlimit_cpu_freq` 未检出；未验证固件是否另有后端 |

本次只读 `present` / `online` 均为 `0-7`，可列的 `/proc` 顶层没有 `ppm`。
这不能推出所有场景都不会热插拔，也不能单凭一个路径缺失把整个资源判为 no-op。
验证逐核行为可比较 `online`、`affected_cpus` 和可用调度状态；核隔离不一定等于离线。
依据：2026-10-05 ADB 观察；资源定义与适配证据见 [resources.md](resources.md)。

### 2026-10-14 复核：`/proc/ppm` 是 ENOENT，不是权限拒绝

`ls -l /proc/ppm/` 与 `cat /proc/ppm/policy/hard_userlimit_cpu_freq` 都是
`No such file or directory`。按 `Sysfs.NodeState` 的规矩，父目录 `/proc` 列得动，
所以这是**目录真的不存在**，不是 SELinux 拒掉搜索。

由此推着改了两处：

1. **实验室「硬上限(每簇)」的说明与事实页矛盾，已改。** 它原来写着
   "写在 /proc/ppm/policy/hard_userlimit_cpu_freq" 且"普通释放不会撤销它" ——
   前半句与本节冲突，后半句没有任何依据。实际行为是：CPU 页每一次区间请求都带着
   这个资源号，释放走同一条 0x17 oneway，用户实测释放有效。
2. **只读面板里四行 PPM 读数是死行，已删。** 每轮读四个不存在的路径，
   界面还显示一行「PPM 软上限」。

**仍未解决**：[resources.md](resources.md) 里 BSP 原文写着
"setClusterHardFreq() is a NO-OP if /proc/ppm/policy/hard_userlimit_cpu_freq does not exist"。
节点不存在，按文档这次写入应该是空操作；但 CPU 页的区间控制在用户手里是生效的。
两种可能：固件另有后端，或效果来自同一请求里的软上限那一对。
**分辨办法就是「逐 ID 测试」单独发 MAX_HL** —— 那是它存在的理由，别删。

### 2026-10-14 实测：四个资源单独发都生效，软硬齐发是冗余的

`/proc/ppm` 不存在，按 BSP 文档硬上限该是 no-op。用 `adb shell service call
power_hal_mgr_service 22` 逐个单独发（policy7，时长 8 秒，发完即释放）实测：

| 单独发哪一个 | 读回 `scaling_max_freq` / `scaling_min_freq` |
|---|---|
| 软 `MAX` `0x404200` = 1500000 | 上限 2100000 → **1500000** |
| 硬 `MAX_HL` `0x40C200` = 1500000 | 上限 → **1500000** |
| 软 `MIN` `0x4194816` = 2000000 | 下限 600000 → **2000000**，cur 跟着上去 |
| 硬 `MIN_HL` `0x408200` = 2000000 | 下限 → **2000000**，cur 跟着上去 |
| 释放（0x17，oneway） | 四项全部回到原值，无残留 |

**结论一：固件另有后端。** 节点不存在没有让这次写入变成空操作，BSP 文档那句
"NO-OP if … does not exist" 在本机不成立。

**结论二：软的那一对就够，硬的那一对是冗余的。** 同一个数值，软的能压硬的也能压，
单独发效果相同。`CpuControl` 现在每次区间请求软硬四项齐发，多两趟 binder、
多两个可能失败的释放点，换不来任何额外效果。

**软硬都冲不破系统包络。** 这与旧调查里"软 MIN=3300000 被常驻上限压在 2300"一致：
那一例的问题不是软或硬，是请求值超出了系统允许的包络（本机约 2000–2300）。
换硬的下限同样过不去 —— 所以这不是"留个硬上限设置给用户"能解决的场景。

**顺带纠正一处误读。** `resources.md` 里 BSP 原文 "Hard limits survive a soft release"
被读成了"任何释放都清不掉它"，实际说的是软硬分开请求时的行为。
**订正写在 [resources.md](resources.md) 那句原文旁边**，这里不重复。

依据：2026-10-14 ADB `service call` 实测，policy7（cluster index 2），
每次时长 8000 ms 且显式释放；8 秒后复查无残留。
`service call` **不要带 interface token** —— 带了 HAL 的 onTransact 会因为
parcel 长度对不上抛 "Allocation size … above allowed limit"。

### 2026-10-14 App 层复核：硬的那一对默认不发，是个开关

上面结论二落成了「设置 → 通用 → 附带硬上下限」，**默认关**。真机开起来之后
`PerfLock` 日志确认每簇发四个资源（软一对 + 硬一对），一次释放全清：

```
0x00400000=300000, 0x00404000=2000000,   ← policy0 软
0x00408000=300000, 0x0040C000=2000000,   ← policy0 硬
…policy4 / policy7 同样各四个…
```

**这个开关一开始是坏的**，而且坏得看不见：设置值写得进 DataStore，界面和
`CpuControl` 都读不回来（`launch` 里串了两个 `collect`，第二个是死代码），
编译单测全过。修法见 [architecture.md](../dev/architecture.md) 的
「一个 `launch` 里只放一个不会结束的 Flow」。换机型遇到"只认硬限"时再打开它。





<a id="cpu-007"></a>
## CPU-007 应用频率时附带放开温控

2026-10-19 增加「设置 → 通用 → 应用时一并放开温控」，**默认开**。
放开温控能让频率请求真正落地；代价是移除系统温度保护，机身更热、更耗电 ——
这是用户明确选择的行为。

规则：应用频率区间时，如果用户**没有手动选过**温控档位，按设备上的配置现挑
**最接近"放开 CPU 温控"** 的一档；手动选过就以手动档位为准。方案里写了
`thermalIndex` 的，按方案执行。

挑法（`ThermalPolicyCatalog.looseIndex`）不写死编号，因为编号在不同机型/ROM 上含义不同。
判据只用 CPU 频率表本身：**40–50°C 每个整数温度的允许频率求平均，平均值越高越宽松**。
完全没有 CPU 频率表段的档位排第一；有段但 `mode=disabled` 的排第二 ——
两者都不压 CPU，但后者的段还在，固件是否始终遵守关闭标志没有运行时证据。

**不看目标温度，也不看首档频率** —— 真机数据里两者都会误导：

| 档位 | 40°C | 42°C | 45°C | 48°C | 40–50°C 平均 |
|---|---:|---:|---:|---:|---:|
| 01 / 08 / 09 | 无 CPU 频率表 | — | — | — | 不压频 |
| 05 | 2850 | 2500 | 2200 | 2200 | **2318** |
| 02 / 12 | 2300 | 2300 | 2300 | 1400 | 2282 |
| 10 | 2500 | 2500 | 2200 | 1700 | 2136 |
| 18 | 2100 | 2100 | 2100 | 2100 | 2100 |
| 00 | 2200 | 2200 | 2000 | 1700 | 2082 |
| 11 | 2000 | 2000 | 2000 | 1700 | 1973 |
| 07 | 2200 | 2000 | 1500 | 1300 | 1636 |
| 13 | 2000 | 1800 | 1400 | 800 | 1418 |
| 03 | 1500 | 1500 | 1200 | 1100 | 1236 |

（单位 MHz，cluster2；数据来自本机 `.local-baselines/thermal-crack/plain`。）

`07` 的首档是 3.3 GHz，平均却只排到倒数第三 —— 这就是不能拿首档频率或目标温度判断的原因。
`02/12` 在 42°C 与 `05` 接近，但 48°C 掉得更狠；平均下来 `05` 最宽松。

不同档位可能用不同传感器（`ap_ntc` / `tz_shell` / `tz_game_shell`），摄氏度不是同一个
物理量；这里只做相对比较，不据此断言绝对温度。

`permanent=Yes` 不降权：它是策略本身的属性，恢复由 `ThermalPolicyController` 负责。
用户手动选过档位时，仍以手动选择为准。

### 2026-10-19 回归：放开温控后软上限被抬回硬件最高

真机日志（22:05）：请求 policy4 2100–2300、policy7 2500–3100，读回却是
`2850-2850` / `3250-3250` —— 正好是硬件最高频。原因是**放开温控（策略 08）之后，
厂商 boost 会重新写 `scaling_max_freq`，把软 MIN/MAX 顶掉**。

同一时刻用 binder 手动下发**硬限**（`MIN_HL` / `MAX_HL`）2100–2300 / 2500–3100，
读回立刻变成请求值并保持。结论：

- 软限只在温控还在时有效；放开温控后必须带硬限；
- 实现上 `AppContainer` 把 `hardLimits` 改成 `用户硬限开关 || 放开温控开关`，
  所以默认（放开温控开启）就会发硬限；
- 用户手动关掉放开温控时，仍按他自己的硬限开关走；
- 设置页里「附带硬上下限」在放开温控开启时**隐藏** —— 它此时是强制的，
  留一个看起来能关的开关只会误导。只有放开温控关闭时才显示。

这一条是“限了上限却被跑满”的根因记录，改 CPU 下发路径时别把硬限又去掉。

2026-10-22 修正选档顺序：**完全没有 `[mtk-cpu-table-mapping]` 段的档位优先于
“有段但 `mode=disabled`”**。本机 01 没有这一段，08/09 有段但关闭；两者温度都不压 CPU，
但关闭只是配置值，固件是否始终遵守没有运行时证据。08/09 里那段 46°C 的表也不再
作为生效内容展示。因此本机现在自动选 **01**，不是 08。
表都被关闭时才看 `isolate`：关闭的优先（核心隔离也是限制手段），再看目标结温、
皮肤阈值；完全并列才取小编号。本机 01 的 isolate 是 enabled，08/09 是 disabled，
所以若比较范围里没有 01，08/09 仍会排在其它档前面。

**“系统上限低于请求下限”不再硬锁。** 2026-10-22 日志：请求 policy4 2500–2800 /
policy7 3100–3300，读回 `2500-2500` / `3100-3100` —— 系统当时的上限就是 2.5/3.1，
硬下限把区间钉成了一个点。现在区间请求读到这种结果会自动重试一次，**只压上限、
不锁下限**，并在结果详情里说明。点请求（min == max）仍然按用户要求钉住。
重放状态（`lastApplied`）跟着实际下发走，但 `lastRequested` 保留用户原始范围，
快捷开关/亮屏恢复会重新尝试完整区间。

**先切温控、再下发频率。** 2026-10-22 同一份日志：CPU 请求 17:48:30 下发，
17:48:33 切到温控 01 后，读回只剩 1.2/0.6 GHz。切档会让平台重推自己的一套限制，
频率请求先发就可能被顶掉。CPU 页「应用」、切方案和按 id 应用方案都已改成
温控在前、频率在后；温控失败不阻断频率。

## CPU-008 普通档与 BOOST 档是另一层上限（2026-10-22 用户实测）

普通模式下，即使温控已经切到 01，policy4 / policy7 仍分别停在 **2.7 / 2.9 GHz**；
切到 BOOST 档后限制消失。这个 2.7/2.9 不是温控表给的：

- `powerscntbl.xml` 的 2150 / 2160 / 2163 / 2175 场景，C2 max 正好是 2900000；
- 厂商 `CPUFreqPolicy` 的 `LIMIT_PARA_ALL_CORES_27_29G` 数组是 2700/2000/2900。

所以温控档位只解除“温度→频率”的表，**解除不了厂商场景/性能档自己的 MAX**。
BOOST 档之所以“正常”，是厂商换了一套场景限制；而本应用切换性能模式时会主动
调用 `onPerformanceModePause(true)` 释放 CPU 请求，避免两套限制打架 ——
BOOST 下看到的频率是厂商接管，不是我们的区间生效。

已试过但**没有**放宽这层上限的路径：Vivo `0xF0000C00=88000003`（接受句柄、
读回不变）、`BOOST_CPU_MAX_FREQ` 三簇 4095（同样不变）。因此目前没有
“保持本应用区间 + 同时越过普通档 2.7/2.9”的已验证方法。可选做法只有切厂商
性能档，代价是本应用交出频率控制；或在普通档下把区间设在该上限以下。

**它不保证解除皮温驱动的硬上限** —— 那一层由当前策略按皮肤温度动态决定，索引只能
选中"没有 CPU 频率表"的那一档，不能关掉整个温控。

2026-10-19 两次扫描（第二次在桌面、非游戏前台，避免系统按场景重选）：

- 索引 0–18：能读到自己阈值组的至少两个 —— `03` → `40/43/45/47`，
  `13` → `39/41/44/47`；`01/08/09` 读回 `NaN`（没有 `thermalhal-threshold` 段），
  其余大多是 `40/42/45/48/60/80`；
- 索引 19–40，以及 `-1`、`100`、`255`、`1000`：一律读回 `NaN`，没有出现
  `30/30/30/30` 或 `80/80/80/80`（`disable_thermal` / `disable_throttling` 的特征组）。

结论：**没有证据表明任何数字索引能选中 `disable_*.conf`**。超出范围的索引读回 `NaN`
只说明“当前没有阈值表”，不等于 CPU 不再被压频——要证明那一点得做负载下的频率对照，
本次没有做，不能据此把“随便填个越界值”当成禁用温控。

扫描工具是临时 `app_process` 程序，落在 `.scratch/`（gitignore），用完已从设备删除。

关于 `disable_thermal.conf` / `disable_throttling.conf`：同目录确实有这些文件，
但它们**不在数字索引的命名空间里**（加载器按 `thermal_policy_NN.conf` 编号选文件），
`/vendor/etc/thermal` 只读、无 root 也改不了文件名，所以无法通过索引直接选中。
能做的只有上面这套"按配置内容挑最接近的一档"。

参考实现的「解除温控」多走另外两条路：`cmd thermalservice override-status 0`
和 `pem_htp_level`（vivo 游戏温控）。`override-status 0` 是框架热状态覆写，
0 = `THERMAL_STATUS_NONE`（让框架认为不热），**不是所有机型都有效**：它管不到
厂商 HAL/温控守护进程，本机也没有验证过它能不能绕开 PowerHAL 的 2.3 GHz 限制，
所以没有采用。

### 附带问题：档位偶发读不到

2026-10 出现两三次"温控档位读不到"，重装或重启后又好了，看似随机。根因是
**权限状态和服务就绪不是一回事**：权限已授予、`mode` 已是 ADB，但 Shizuku 用户服务
还没绑好，这时列 `/vendor/etc/thermal` 会失败；绑定完成后 `refresh()` 发布的状态
与之前相等，`StateFlow` 不会再次发射，ViewModel 的"补读"分支永远等不到触发。
修法是把 `serviceReady` 放进 `PrivilegeState`，让绑定完成时状态值真的变化，
CPU 页已有的补读逻辑随之执行。改过 Shizuku/权限相关状态时，检查这个字段有没有被绕开。
