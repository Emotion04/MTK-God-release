# 外部实现接入时的判断

接口与命令出处查本目录四份 [固定版本摘录](README.md)；
项目当前边界见 [工程架构](../../dev/architecture.md)，设备结果见 [命令与观测](../../device/commands.md)。
旧的逐功能“已实现 / 未实现”和移植优先级已被源码与现行待办取代。

## 保留的取舍

| 问题 | 本项目的处理 |
|---|---|
| 新入口直接拼命令，绕过原有快照和互斥 | 页面、磁贴、后台任务复用同一控制器 |
| 同一 Settings 键分散在多条权限路径 | `SettingChannel` 统一写入和回读；后端差异在通道内适配 |
| 外部脚本与本项目同时持有性能请求 | 分别记录所有者与释放方式；对照实验记录其他活跃请求 |
| 设置一组推定“默认值”作为恢复 | 使用操作前原值，保存原键缺失状态 |
| 命令被接受就称功能有效 | 按配置、服务状态和可见效果选择判据 |
| 假电量、假温度等状态伪装 | 区分上报状态与物理效果，核对退出后的恢复 |
| 大包脚本夹带未知设置和服务操作 | 依据明确语义接入具体能力，并确认退出行为 |

`pm grant <self> WRITE_SECURE_SETTINGS` 与借用其他 App Context 的注入，
都可能增加独立系统设置写入路径；来源实现中的做法不能直接成为本项目执行方式。
本项目保持统一通道便于归因与恢复。其具体限制来自架构，
不从这份分析扩展成“所有后台任务、所有节点写入、所有新后端永久禁止”。

原分析把同一 UID 下的受控 shell 命令选择也混成了“第二条路径”，范围过宽。
在同一通道中选择 `settings` 或 `content` 是可行的；
需要按键处理回读归一化和失败，而不是为此增加 App 进程权限。
