# 用户文案

本页规定应用文案的表达、资源组织和展示边界；交互布局见 [ui.md](ui.md)。

## 表达与状态

**按最终界面写文案：每条文字只补充当前位置还没说清的信息。**
先看标题、标签、按钮和相邻提示，再决定需要写什么；不要孤立地把每条字符串写成完整说明。

- 标题已说明对象，状态就省略对象。例如“温控档位”下面写“读取失败”，
  不写“温控档位读取失败”；已有“读取失败”标签时，正文不要再重复失败。
- 一条提示表达一个信息。空状态说缺什么，错误说哪里失败，按钮说做什么。
  没有必要的补充就不加正文，不为凑齐“结果、原因、操作”而各写一句。
- 优先用日常中文的短句。删掉不影响理解的主语、铺垫和礼貌套话，
  如“这台机器上”“本软件”“请确认”；必要对象、条件和风险不能为了短而省略。
- 错误摘要不带异常类名、调用过程和原始返回码，这些进入日志或诊断详情。
  恢复办法只在原因或前置条件有依据时给出，不把授权、重启等排障建议拼成通用尾句。
- 失败处先显示面向用户的摘要，原始错误点击后才显示；展示与数据契约见
  [失败结果的展示边界](architecture.md#失败结果的展示边界)。
- 并列选项保持同一层次。区分能力不可用与效果尚未确认；请求被接受只说明请求结果。
- 长任务就近展示进度、最终结果和恢复状态；状态标签作为独立信息层级。

| 展示位置与已知条件 | 文案 |
|---|---|
| “温控档位”标题下，读取失败 | 读取失败 |
| 同一位置，成功列出目录但未找到配置文件 | 无配置文件 |
| 同一位置，已确认缺少 Shizuku 授权 | 未授权 Shizuku |
| 独立通知，没有标题说明对象 | 温控档位读取失败 |

这些示例依赖所在位置和已知条件，不是统一替换词表。未读到不能直接写成不存在，
列表为空也不能直接写成不支持；必要时保留不确定性。

例如“温控档位”下先显示“读取失败”，点击旁边的“显示更多”后才显示原始错误。
详情入口的文字和无障碍描述也使用资源，不能用异常类名充当按钮名称。

数值与其依据和时间范围一致：当前值、历史值和估计值明确区分。
当前值不可读时使用未知状态或占位符；必要说明帮助用户判断或操作。
例如摘要显示“DDR 频率不可读”，尝试过的路径放在诊断详情。

## 存放位置

应用编写的用户文案放入 `res/values/strings.xml`，包括标题、短按钮、说明、
错误摘要、通知和无障碍描述。设备原文、用户输入、路径、协议标识、构建标识、
报告原始字段和工程日志按数据处理；展示这些数据的标题和说明仍使用字符串资源。

Compose 使用 `stringResource()`，其他 Android 展示边界使用 `getString()`。
ViewModel 和控制层优先返回状态、错误类型和数据，由展示边界选择文案；
通知等非 Compose 展示也在各自的展示边界读取资源。

Android 允许在 `res/values/` 下用多个 XML 文件定义字符串，资源由 `name` 标识。
本项目默认使用 `strings.xml`；只有维护需要明确时才按功能拆文件。
默认资源应完整；翻译放入相应语言目录，保持资源 key 一致。

## 模板与资源命名

- 完整语句使用一个资源模板，变量采用位置占位符，如 `频率 %1$s MHz`。
  数值、日期和时间按展示需要格式化后传入，保留完整语句的语序。
- `plurals` 用于语言的语法数量变化；Compose 使用 `pluralStringResource()`。
  模板包含数量占位符时，分别传入选择复数形式的数量和填入模板的数量。
  业务上的空状态、单选和多选分别按其含义组织文案。
- key 沿用 `<对象>_<角色>` 风格，如 `thermal_card_title`。
  相同文字只有含义、使用语境和翻译要求一致时才共享 key。
- **`<对象>` 是功能域，不是它当前所在的页面。** 一个功能的入口会搬
  （温控档位从实验室搬到了 CPU 高级设置），按页面取的名字就会变成假的：
  `lab_choice_note_title` 讲的是温控档位说明，和"实验室"没关系；
  `thermal_light` 名字像温控档位，实际是 Android Thermal HAL 的节流等级。
  按域命名，将来搬走时 key 和引用都不用动。反过来，**按页面命名的 key
  就是一条待清理的技术债**，加之前先想清楚这个名字一年后还成不成立。
- 同一个底层能力被多个界面复用时，文案按**那个界面在讲的事**命名，
  不按底层模块名。例如"按应用温控"和"温控档位"共用同一个 PowerHAL 资源，
  前者是 `app_thermal_*`，后者是 `thermal_*` / `policy_*`。
- 固定且无需翻译的品牌名、技术名称可以使用 `translatable="false"`；
  需要本地化的名称按语言提供资源。

## 选项与枚举

`domain/model/` 保存身份和数据，保持与 Android 资源解耦，这是本项目的依赖约定。
其选项文案在 `ui/OptionLabels.kt` 集中映射；有限枚举使用穷尽的 `when` 表达式。
已有 Android 相关选项定义可持有 `labelRes` / `descriptionRes`，展示处读取资源。

动态名称由资源模板和数据组合，例如簇名中的核号范围。
用户保存的方案名称和设备返回的标识保留原值。

## 报错分两层，不许合成一句

**一条失败是两个字段，不是一个 `String`。**

```kotlin
data class Failure(
    val summary: Message,       // 给人看的一句话
    val detail: String? = null, // 原始错误，默认收起
)
```

| 层 | 内容 | 默认 |
|---|---|---|
| 摘要 | 结论，简短，不带内部标识符 | 可见 |
| 详情 | 异常类名、消息、返回码、节点路径 | 收起 |

展示统一走 `ui/components/FailureNote.kt`：摘要永远可见，详情藏在一次点击之后
（弹窗、限高滚动、**带复制**）。多条明细（每个键的旧值新值、每个失败项）用
`ExpandableDetails` —— 那是列表；`FailureNote` 负责"一句结论 + 一段原始错误"。

**为什么必须拆。** 合成一句的后果见过不止一次：摘要里同时出现异常类名、授权检查、
更新后的排障办法 —— 那是把开发者的排障笔记直接搬上界面。用户要的是"成没成"，
不是"该去哪儿点"。

硬规矩：

- **摘要里不出现**异常类名、资源编号、节点路径、返回码。这些进 `detail`。
- **不给所有异常配同一套建议。** 「请检查授权」「重启后重试」只在确实因为这个原因
  失败时才写；分不清原因时，摘要只说结果，证据放进 `detail`。
- **不要求用户跨页面翻日志。** 排障信息跟着失败位置走；日志可以有，但是备份，
  不是唯一入口。
- **详情必须可复制。** 用户反馈问题时，能不能一键复制决定他愿不愿意配合。

## 维护与验证

新增文案使用资源；修改旧页面时迁移涉及的历史文案。
工具可以辅助提取，维护者复核文案与数据边界、占位符类型、语义共享和展示位置。

交付前把涉及的文字按实际界面组合复核，包括动态值填入后的结果：
是否重复标题或状态，删去某段后是否仍能理解，恢复建议是否有依据。
新增或迁移进资源的文案也要做这项复核；资源化完成不等于表达合格。

运行 `python tools/check_strings.py`：资源引用和硬编码基线用于检查回归，
字符串形态匹配仅提示复核。正则有漏检和误报，修改时还需查看涉及的展示路径；
检查通过不能代替编译及受影响交互的验证。

当前形态扫描只覆盖 `feature/`、`ui/` 的 Kotlin 字面量，不检查 XML 资源的表达，
也不判断相邻文字是否重复、中文是否自然；这些由上述界面复核负责。

检查按**文件所在层**判定，不按字符串长什么样：`domain/` 出现中文即失败；
`feature/`、`ui/` 的中文应全部进资源；`data/` 里工程日志与报告原文按数据处理，
其余 —— 尤其是返回给上层的说明 —— 按文案算。一个中文是不是"日志原文"看它
**是谁的实参**：`AppLog.i(...)`、`emit(...)`、`appendLine(...)` 里的是，别处不是。

确实要展示的设备原文、协议标识，在该行或上面几行写 `ui-check:ignore` 显式豁免。
整个文件的中文都只进诊断轨迹与工程日志时（如 `PerfLockController`），
在文件前部写 `ui-check:ignore-file: <理由>` —— **必须写理由**，
没有理由的文件级豁免应当被当作没有。

两个检查都挂在 `preBuild` 上，每次构建都会跑；没装 Python 的机器用 `-PskipChecks` 跳过。
