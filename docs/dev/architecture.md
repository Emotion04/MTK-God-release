# 工程架构

本页说明跨功能的契约。目录、字段和常量的具体实现查 `mtk-optimizer/app/src/main/`；
修改相关代码时同步更新受影响的契约。

<a id="device-adaptation"></a>
## 分层与状态

| 边界 | 职责 |
|---|---|
| Compose 页面与 ViewModel | 展示状态、收集意图；不直接发系统控制命令 |
| Repository / 控制器 | 组织读写、校验、请求所有权和恢复 |
| `DaemonExec` / Shizuku UserService | 执行受控命令、返回退出码和输出 |
| 设备适配与协议 | 发现能力、构造请求；明确机型和权限边界 |

可持续的偏好和恢复快照由数据层持有；页面草稿与显示状态由对应 ViewModel 持有。
设备 I/O 离开主线程；采样随页面可见性和生命周期停止。页面切换不应意外重置正在编辑的状态。

`domain` 保留身份和数据，展示层选择资源并组合动态名称，见 [wording.md](wording.md#选项与枚举)。

**依赖方向固定为 `feature → domain/data`、`data → domain`；`domain` 不依赖 Android、Compose
或 PowerHAL。** 页面通过 ViewModel 与控制层发起系统操作，由控制层维护所有权、串行执行和恢复线索。

## 状态读取的位置决定重组范围

**在哪个组合作用域里读 snapshot 状态，决定了那个状态一变时多少东西要重组。**
这不是微优化，是这条架构里最容易踩、且踩了很难看出原因的一条。

每帧都变的状态（`PagerState.currentPageOffsetFraction`、动画进度、滚动位置）
尤其要注意：读它的人必须是**最小的那个 composable**。

```kotlin
// 错：读取发生在 AppNavHost 的作用域里 —— 每一帧整个 NavHost 连带所有页面失效
pageOffset = pagerState.currentPage + pagerState.currentPageOffsetFraction

// 对：传 lambda，读取发生在底栏内部；再把会动的部分拆成单独一个 composable
pageOffset = { pagerState.currentPage + pagerState.currentPageOffsetFraction }
```

配套几条：

- **会变的值用 lambda 传，不要传求值结果。** 调用点只差一对花括号，失效范围差一整棵树。
- **会动的部分单独拆 composable**，别和静态内容写在同一个函数体里。
- **像素位移用 `Modifier.offset { }`**（lambda 版）而不是 `offset(x)`：
  前者把读取推迟到布局阶段，位置变化只触发重新布局，不触发重组。
- **`data class` 状态里的 `Map` / `List` / `Set` 对 Compose 是不稳定类型**，
  任何字段变化都无法跳过重组。状态类字段多、页面重的时候值得评估。

读一次状态的开销可以忽略（一次字段访问）；代价全在**它触发的重组范围**上。

## 提权命令的输出必须校验 `[exit]` 标记

`RuntimeUserService.exec` 有两种返回：

| 情况 | 输出 |
|---|---|
| 正常 | `正文` + `\n[exit] 0` |
| 服务端自己抛异常 | `ERROR: …` —— **没有 `[exit]`** |

**所以取正文前必须先确认标记在。** 用 `substringBefore("[exit]")` 是错的：
标记不在时它返回**整串错误文本**，于是同一处错误被三种方式静默吞掉 ——

- 读节点：错误文本被当成"文件内容"返回，调用方以为读到了值
- 写节点：正文非空 → 报告**写入成功**（一次失败的写入显示成成功）
- 列目录：错误行被当前缀过滤掉 → **空列表**，和"目录里真的没有文件"一模一样

`DaemonExec.parse` 与 `VivoReply.output` 早就要求这个标记（`lastIndexOf` 找不到就返回 null），
`Sysfs.body()` 后来补齐同一条规矩。**新增任何解析 `exec` 输出的代码都走这两处，不要自己 `substringBefore`。**

**剥标记只有一份实现。** `Sysfs.body()` 现在直接调 `DaemonExec.parse`，自己不再写第二套：
包装格式是 `<stdout>\n[stderr] <stderr>\n[exit] <code>`，两处各写一遍的后果是行为悄悄分叉 ——
曾经 `Sysfs` 不剥 `[stderr]`，于是命令写到标准错误的内容会混进"文件内容"和"文件名"里，
而 `DaemonExec` 那边早就剥掉了。规矩相同的事不要实现两次，哪怕第二次看起来只有三行。

配套：**"没读到"和"确定没有"必须分开。** 列目录用 `Sysfs.listOrNull`，返回 null 表示没列成；
界面要把这个区别显示出来（`thermalReadError` 就是这么来的），不要渲染成一片空白。

### 判"不存在"的身份，必须和产生这条判词的身份一致

`Sysfs.states()` 的 ABSENT 来自提权 shell 的 `No such file or directory`。**能佐证这句话的，
只有同一次 shell 调用里父目录的判词**，不能是 App 进程自己的 `File.canRead()`。

原因是 SELinux 按**域**授权：同一个目录完全可能 App 读得动而 shell 搜不动。拿 App 的
PRESENT 去佐证 shell 的 ENOENT，是两个身份在对话 —— 那个 ENOENT 其实是"不许你知道"，
却被佐证成"真的没有"，于是能用的功能被置灰。`/proc/perfmgr` 就是现成的例子：
它是 `dr-xr-xr-x`，DAC 上人人可读，而 shell 的 `cat` 得到 Permission denied；
里层 `thermal_policy` 得到的是 ENOENT 而不是 EACCES（内核故意如此，以免泄露路径是否存在）。

所以实现上分两张表：App 自己的判词只用于回答"存在"（打开过即是证据），
`shellStates` 只收 shell 的判词，父目录佐证只查它。**同理，`readMany` 的直接读只决定
"要不要再问 shell 要一次"，不参与任何存在性判断。**

反方向同样成立：**服务没连上、绑定超时、调用抛异常是三件事。**
`PrivilegeManager.powerHalAcquire` 用 `CallResult` 而不是可空的 `Int`，
否则一次 binder 崩溃和一次忘了开 Shizuku 在界面上长得一模一样，点"显示更多"也没有东西可看。

### 读不到判据，就别写

**一次写入只有一个理由：为了改变某样能被观察到的东西。** 观察不到还写，
就是白白改一次设备状态，换来界面上"读回失败"四个字。

2026-10-15 在实验室抓到这条被违反：`LabController.apply` 第一步读 `before`，
第二步照发不误，第三步才发现 `after` 也是 null，报"读回失败"。`/proc/perfmgr/**`
那一族正是这个情形 —— 目录存在但 SELinux 拒搜，里层文件报 ENOENT、父目录报 EACCES。
`Sysfs` 把它正确判成 **UNREADABLE 而不是 ABSENT**（所以不该置灰成"本机不支持"，
功能可能仍然有效，真正的通道是 PowerHAL opcode），但 caller 只拦了 ABSENT，
于是把"读不到"当成了"可以先写写看"。

现在 `apply` 和 `sendRaw` 都在下发前拦一道：`before == null` 就不写，
判定记账成"读不到判据节点，未下发"。

**这和上面那条不矛盾。** "读不到不许判不存在"说的是**不要因为看不见就禁用功能**；
这里说的是**不要因为看不见就动手**。两件事的方向相反，判据是同一条：看不见就是看不见。

## 同一资源的多个写入口要有一个仲裁者

一个系统资源只能有一个写入口。**多个界面能改同一个东西时，正确做法不是"各自注意别冲突"，
而是把写收敛到一个控制器**，界面只表达意图。

反例是温控档位：CPU 页「应用」、按应用温控、实验室三条路各自 `PowerHal.acquire`、
各自持句柄，释放时只放自己那一把。用户可能同时被两边持有，现象是"我设了却没用 /
设完又弹回去"，而三处界面各自显示正常 —— 谁也不报错，因为谁都没做错。
PowerHAL 对同一资源的多个请求怎么合并没有文档，所以唯一的稳妥答案是**一次只有一把句柄**。

仲裁者（`data/thermal/ThermalPolicyController.kt`）要做的四件事：

1. **串行化。** acquire/release 有顺序含义，并发会拿到互相不知道的句柄。
2. **记住每个来源的意图，而不是只记住当前值。** 温控档位的常驻意图是
   `userIndex ?: appRuleIndex`（用户刚做的决定优先于轮询）；临时档到期后
   由控制器把常驻意图放回去。只记当前值的话，一次实验会把用户设好的档位吃掉。
3. **先拿新的再放旧的。** 拿不到新句柄时保留旧的 —— 失败不该把用户的现状弄丢。
4. **暴露一个共享的 `StateFlow`。** "CPU 页改了实验室立刻看见"不需要任何同步代码 ——
   所有读方读同一个流。各读各的（自己读节点、自己读 dumpsys）必然各显示各的。

相同取值也要换句柄，不能只改来源标签：**临时档到期是固件行为，我们收不到通知**，
只改标签会让用户那一档跟着没。

### 温控档位为什么是"先拿后放"，以及为什么不能反过来

**先纠正一条没依据的说法。** 这里原来的理由是"反过来有一个'两把都没有'的窗口，
设备回到默认状态，用户看到的是'切档时卡了一下'"—— 那句话从初版提交起就在，
**是设计期推断，没有实测依据**，却写成了观测结论。已删。

真实情况是两种顺序的中间态都不可推理，而且不可推理的方式不同：

| | 中间态 | 能不能推理 |
|---|---|---|
| 先拿后放（现状） | 新旧两把并存，固件选哪一把无文档 | **不能** —— 见下 |
| 先放后拿 | 200 ms 无请求，回落到 `thermal.conf` | 能，但可能比两端都激进 |

**索引不在一个尺度上**（[温控配置索引](../thermal/configs/README.md)，cluster2 首档）：

```
00=2600000  02=2300000  03=1700000  05=2850000  07=3300000
10=2800000  11=2000000  13=2600000  18=2100000
```

03 最保守、07 最激进，**索引号大小和激进度无关**。所以"两把并存时固件选哪把"
连"取大/取小"都推不出来 —— 没有大小可言。这是先拿后放唯一的不确定处，
窗口只有一趟 binder。

而无请求时固件回落到 `thermal.conf`（[THERM-001](../thermal/facts.md) 有干净启动对照：
清除请求并重启后默认行为与主配置相符；该文件 cluster2 11 档从 28°C 开始，首档 3100000）。
往保守档切的那 200 ms 反而比目标档更激进。

**所以真正的决定因素不是中间态，是失败路径**：先拿后放拿不到新句柄时旧的还在，
用户原设置原样保留。这一条现在更硬了 —— `PerfLockController` 那边已经补上
"acquire 失败后恢复上一份请求"（`restoreLastRequest`），等于把先放后拿的劣势
自己关掉了；而温控这边**不需要**那一层，因为先拿后放从来不会把旧句柄丢掉。
两种顺序各自守一个不同的失败，别顺手统一。

两种顺序都不做成设置项：这不是用户层面的偏好，是 binder 合并语义。

判据用资源的**资源号**（`feature.baseId == THERMAL_POLICY_RESOURCE`），
不用界面的 key 字符串 —— key 是给人看的，改个名字不该悄悄把这条路改回旧的竞争行为。

## 链式调用换行后紧跟 `[key]` 会被当成集合字面量

```kotlin
// 错：报 "Collection literals outside of annotations are unsupported"，
// 而真实原因完全是另一件事。
val items = state.groups.flatMap { it.second }.groupBy { it.key }
    [entry].orEmpty()

// 对：先落到 val 再取下标。
val byEntry = state.groups.flatMap { it.second }.groupBy { it.key }
val items = byEntry[entry].orEmpty()
```

Kotlin 把换行后的 `[` 当成新语句的开始。这个报错信息离真实原因很远，
在 `AppNavHost` 里写带参数路由时容易撞上。

## 一个 `launch` 里只放一个不会结束的 Flow

DataStore 的 Flow 是无限流，`collect` 不返回。串写成两句，第二句是死代码：

```kotlin
// 错：第一句永远不返回，第二句没人执行。
viewModelScope.launch {
    repo.a.collect { … }
    repo.b.collect { … }   // 死代码
}

// 对：一个 Flow 一个 launch。
```

2026-10-14 真机验证「附带硬上下限」开关时抓到的就是这个：开关**写得进去**
（DataStore 里确实有值），界面和 `CpuControl` 都**读不回来**，表现是"按了没反应"。
同一个错在三处——`SettingsViewModel`（一处串四个，后三个全死）、
`AppContainer`（`freqHardLimits` 喂给 `hardLimits` 的那条，比界面那条更要命）。
编译、单测、静态检查全过，只有真机点一下能发现。


## 改动自查清单

合并 CPU 或界面改动前逐条确认。**每一条都对应一个真实发生过的故障**，不是泛泛的最佳实践：

1. 点一下选单值，产出的是一个归一化后的值，**不依赖手势方向**。
2. 选区间时下发 `low <= high`，且只发软限（`MIN`/`MAX`）那一对。
3. 每次 apply 都先释放旧句柄再申请新的。
4. 改了 `IRuntimeService` 的 AIDL 面就要把 `PrivilegeManager.USER_SERVICE_VERSION`
   加一。**不加的后果是静默的**：Shizuku 按 tag/version 留着旧的 daemon UserService，
   新包装上之后旧的 AIDL 实现还在，新的 PowerHAL 事务被拒 —— 而界面看起来只是"没生效"。
5. 界面能区分「已生效 / 不可用 / 读不到 / 未验证」四种状态，不把未知显示成成功。
6. 新增的读取路径没有阻塞调用落在 `viewModelScope` 的 Main 上（见上一节）。
7. `git status` 里没有构建产物、第三方原始资料或云同步临时文件，除非明确要求提交。

## CPU 请求所有权

CPU 频率操作由 `CpuControl` 协调。apply/release 串行执行，记录每个请求的所有者与句柄；
释放失败时保留句柄和恢复线索。单值、区间、恢复与后台重放共用这条协调路径。

**一次应用是有序事务，顺序不能换**：读出当前句柄 → **先释放旧句柄** → 释放失败就中止，
既不发出新请求、也不覆盖旧句柄 → 等 oneway 释放排队完成 → 再发一次完整请求数组 →
存下新句柄。反过来写（先 acquire 再 release）会让新旧两个请求同时生效，而服务会合并
活跃请求 —— 下限取最大、上限取最小，结果是任何一方都没想要的区间。

返回句柄只证明请求被接受。通过可用的策略读回观察结果；读不到时返回未知，
不把未知当成成功、零值或节点不存在。CPU 能力见 [当前事实](../cpu/facts.md)。

**`CpuControl.Status` 只放有人读的字段。** 曾在这里放过两个只写不读的，都已删：

- `baseline` 是 `CpuControlStore.baseline` 的内存镜像，零读者。
- `releaseIncomplete` 想表达"释放后内核没回到基线"，**永远不可能诚实地成真** ——
  它能比的只有那份基线，而基线当年存的是硬件能力，不是请求前的当前限制。
  **拿两个不同的量相比，比出来的差说明不了任何事。**

顺带修掉了根因：`captureBaselineIfClean` 现在记的是请求发出前的
`scaling_min/max_freq`（当前限制），不再是 `cpuinfo_*`（硬件能力）。
要比较两个时刻的限制，用 `CpuLimitReading.limitsText()` —— 不带当前频率，
那个值每毫秒都在变，带上就永远比不出相等。

**释放自检不做，这是决定不是待办。** 读回本来就有：`releaseLocked` 里那次
`sampleLimits(clusters, "释放")`，消息 `cpu_release_done_current` 印的就是
"释放操作已完成 · 当前 <limits>"。当初想补的只是一个布尔判词，而它三条都不成立：

1. **差值说明不了我们失败。** 厂商电源服务自己也在压频率（见
   [温控事实](../thermal/facts.md) 里皮温驱动上限那条），差可能来自它。
   这时候报一句"释放失败"是假的。
2. **判词没有下一步。** acquire 失败可以重试；release 失败之后句柄已经从我们的
   记录里消失，App 侧没有任何补救动作可做。
3. **用户看得见。** 读回的数字就在释放结果里，比 WiFi 图标还直接 ——
   不需要再替用户判断一遍。

所以规矩是：**释放后的读回是信息，不是判词。**

判据可以检查：**一个字段从没有人读，就该问它是等着被用，还是本来就没人要。**
`observedLimits` 属于前者 —— 它在四个点被写，接进 `DiagReport` 和 `DeviceSnapshot`
之后才有读者。别把两类混成"都是死代码"一起删。

## 「释放」的语义：App 加的全撤

CPU 页的「释放」不只放频率句柄。凡是 App 在后台长期持有、用户按了释放却还在跑的，
都在这一个动作里收掉，否则就是用户看不见的残留：

| 一起停掉的是什么 | 为什么必须一起 |
|---|---|
| `CpuReapplyService` | 它定期重新下发频率，不停就把刚释放的放回去 |
| `AppThermalService` | 每 2 秒照一次前台应用，不停就把温控档位放回去 |
| `ThermalPolicyController.releaseAll()` | 温控档位是独立资源，频率放了它还在 |

**顺序是先停来源、再清结果。** 反过来（先 `releaseAll` 再停服务）中间那一次轮询
会把档位重新拿起来。而服务自己的 `onDestroy` 会 `applyAppRule(null)` 收尾，
那个 `null` 撞上已清空的状态会被 `push` 的早退条件挡掉，不会二次下发。

**实验室那一把也要撤，这是同一个洞的第三种漏法。** `LabController` 有**自己的**
`PerfLockController`（name = `"lab"`），句柄存在另一个 DataStore 槽里 ——
`cpuControl.release()` 只放 `"cpu"` 那一把。漏了它：用户在实验室长期保持了一个请求，
回 CPU 页点释放，频率回来了，那个请求还在，此后的读回全被它压着，而两边都不报错。
温控档位和按应用温控是前两种漏法，三种都已修。

**请求的寿命归谁，决定了"离开页面"要不要显式释放。** 实验室的请求由 daemon
UserService 发出、句柄落 DataStore，**离开页面不会自动消失** —— 所以两个持有请求的
ViewModel 都有 `onCleared()` 调 `LabController.reset()`。
`CpuReapplyService` 那边的对应决策是 `START_NOT_STICKY`：进程死了没有_handler_能释放，
静默重启只会拿着过期状态重新下发。

## 杀 App 不会释放请求（2026-10-14 真机实测）

发请求的是 **daemon UserService 进程**，不是 App 进程。实测：

```
启动 App        → magicau.mtkcontroller:runtime  PID 21951  PPID 1
                  magicau.mtkcontroller          PID 23556
am force-stop   → :runtime 仍在，App 进程消失
```

`PPID 1`（挂在 init 下）已经说明它不随 App 走，`force-stop` 之后依旧存活印证了这一点。
**所以 App 被杀 ≠ 请求被清。** 用户在实验室"长期保持"一个请求后划掉 App，
那个请求继续压着频率，而界面上什么都看不出来。

**因此一键释放不是可选的补充，是必需的补救。** 它成立的原因也在这儿：
`:runtime` 还是同一个进程，句柄号存在 DataStore 里，重新打开 App 仍然释放得动。
（旁证：`adb shell service call … 23 i32 <handle>` 能释放**上一条 adb 命令**拿到的
句柄，而每条 `adb shell` 都是新进程 —— 句柄在 HAL 侧只是个稳定编号，不绑进程。）

**没做的根治**：把"长期保持"从 `durationMs = 0` 改成"有限时长 + 屏幕活着时续期"。
那条能真正做到 App 一死请求自己到期，还能避开"释放一个已被复用的句柄号"的风险。
当前选择是一键释放兜底，局限写在了 `AppContainer.releaseAllRequests` 的注释里。

**亮度守护不在这个集合里。** `ThermalBrightnessService` 是"守"不是"改" ——
它不持有任何 PowerHAL 请求，只在系统因发热压暗时把用户选的亮度放回去。
而且它的开关有两个界面在写（首页无条件起停、工具页只认 LEGACY 后端），
从 CPU 页去停它会让偏好和实际运行状态不一致 —— 那是它自己那一轮的事。

## cpufreq 节点：路径一份，读法各人自己定

cpufreq 那六个节点（`scaling_min/max/cur_freq`、`cpuinfo_min/max_freq`）的**路径与解析**
只在 `data/cpu/CpuFreqNodes.kt` 一处，谁要读都从那里取。

**为什么非要一份不可**：这三个限制节点的"拼路径 → 读 → toLongOrNull"以前在五处各写一遍
（`CpuControl.readSnapshot`、`CpuViewModel.readCaps`、`CapabilityProbe.readAppliedLimits`、
`CpuScanner`、`LabProbe`）。抄五份就会漂，而最贵的一种漂法是**读取身份不同**：
验证那条路提权补读得到，展示那条路只按 App 身份直读 —— 于是"控制验证通过、界面却显示
未知"，用户看到一个自相矛盾的屏幕，两边都不报错。

**但不该统一的正是读法**。直读还是批量读、要不要提权补读，是业务区别：

| 调用方 | 读法 | 为什么 |
|---|---|---|
| `CpuControl.readSnapshot` | 批量 + 提权补读 | 要看到系统**真正生效**的值，否则验证没意义 |
| `CpuViewModel.readCaps` | 逐条直读 | 要反映 **App 身份**能看到的值；读不到就显示未知 |
| `CpuScanner.scan` | 直读 + 提权补读 | 问的是"这台机器有没有这个节点" |
| `CpuScanner.currentFreqs` | 只读 `scaling_cur_freq` | 1 Hz 采样器，别为"统一"多读两个节点 |
| `CapabilityProbe.readAppliedLimits` | 逐条直读 | 只想确认"刚写进去的那两个值成了没有" |
| `LabProbe` | 一次批量拿全 | 它本来就要把该读的都读回来 |

为了整齐把展示也改成提权补读，等于把"读不到"显示成"读到了" —— 那是
上面那条「不把未知当成成功」禁止的事。

另外两族节点**不归它管**，别再往里加：`scaling_governor` / `related_cpus` /
`affected_cpus` 是别的能力（调速器、核归属），`cpuinfo_*` 是硬件能力而非当前限制 ——
紧急恢复要的是前者，验证下发结果要的是后者，别互相替代。目录本身有
`CpuFreqNodes.dir(policy)`，给"要读的节点不在这六个里"的调用方用
（调速器、`affected_cpus`、原始测试面板里用户手输的节点）。

不同性能控制器可以拥有各自请求，但可能作用于同一固件策略，必须分别释放并在诊断中说明运行状态。
恢复只处理自己持有的请求；`finally` 不能覆盖进程死亡，跨进程恢复依赖持久快照和服务状态。
请求时长和续期策略按已验证的协议使用；改变到期语义前先验证服务行为。

<a id="transaction-code-detection"></a>
协议与 Binder 事务码按 [cpu/protocol.md](../cpu/protocol.md) 查证；
适配新服务时先确认接口，再决定是否发控制请求。节点发现区分存在、不可读与未检出。

## 系统设置与恢复

系统设置经 `SettingChannel` → `DaemonExec` → Shizuku UserService 写入。
同一通道可按 ROM 使用受控的 `content` 或 `settings` 命令，统一记录身份、退出码和读回结果。
新增后端在这一边界适配，不增加 App 自身的系统设置写入权限或借用其他进程的 Context。

`SettingChannel` 当前按字符串精确比对读回；新增键遇到数值归一化时，在该层按键定义验证规则。
文件导出的 `ContentResolver` 操作属于存储接口，与系统设置写入是不同职责。

开启前保存原值以及“原键不存在”的状态，关闭时恢复该快照。原值不是零值或推定出厂值。

**原值只有一份实现：`data/settings/RecoverySnapshot`。** 规则写进它之后，调用方只剩
「什么时候取、什么时候释放」。2026-10-17 之前触控（`touch_originals`）和厂商功能
（`vivo_tweak_baselines`）各写了一遍同样的读、合并、删，游戏加速又有一套存活标记 ——
三处都符合当时的规范，因为规范只写了规则、没写「只能有一份」。现在键空间按功能分
（`RecoverySnapshot.TOUCH` / `VIVO`），新增功能注册一个新空间即可，不再自己存快照。

快照**不进导出备份**：它记的是这台机器的原值，不是用户的选择；导到另一台机器上
指的不是同一个东西。备份里的系统状态另有 `StateBackup` / `OwnedKeys`。

首次打开的干净基线（`BaselineSnapshot`）是第三件事：它是**诊断报告**用的只读存档，
采一次永久保留，不参与任何功能的恢复。

**升级后不把旧值当"当前默认"。** 同一版本进程被杀，快照是写之前的真原值，必须保留；
换了 `versionCode`，`TweakRepository.migrateIfVersionChanged()` 会把上一版留下的触控项与厂商功能
按快照**还原**，然后记下新版本号。还原失败的项保留快照、记日志、在导出报告里可见 ——
不悄悄丢弃，也不退而求其次把"我们自己写进去的值"当成默认：那样用户改错之后再也没有系统默认可回。
同一键由多个功能使用时明确所有者与组合语义，避免互相覆盖和错误回滚。
写入、读回和恢复都应有可区分的结果。

### 一个开关的两个真相：偏好和实际在跑的东西

开关的**偏好**和它**驱动的那个东西是否真在跑**是两件事，派生状态的判据只能有一份。
反例是亮度守护：`thermalBrightness` 偏好和 `ThermalBrightnessService` 的起停，
原来在两个界面各写一遍，而且写得不一样 —— 首页无条件起、工具页只认 LEGACY 后端。
同一个开关两种行为，用户在两个页面看到的状态会互相矛盾，而两边都不报错。

判据收敛到 `TweakRepository.brightnessGuardRuns`（`on && backend == LEGACY`），
两个界面都读它。和上面 `touchItems` / `touchEnabled` 是同一条规矩。

### 触控项：开关决定用不用，数值决定写多少

`TouchItems` 里的项分成两类。`render_vsync`、`sf_latch` 这类背后是布尔标志，
开关就是全部语义。**按下防抖和指针速度背后是数** —— 前者是四个毫秒/档位键，
后者是 0–7 的档位，原来只给一个写死的出厂预设，等于只让人二选一。

现在 `TouchKnob.numberRange` 非空的旋钮在界面上是滑杆加输入框（滑杆粗调、框精调）。用户填过的数存在 `touch_values`，
键为 `itemId|旋钮键名`；写设备时 `onValueOf` 优先用填过的数，否则用预设。

**本机没有的项不列。** 进页面时对一遍每个键：prop 或 settings 读回字面量 `null`
（`CmdSettingsProvider` 对不存在的键就返回它）才算缺。整项的键**全部**读不到才隐藏 ——
`_single` / `_double` 这种部分缺失可能只是 ROM 只做了分支，隐藏整项会连带删掉真能用的。
凭空建一个没人消费的键，界面照样显示成功，用户会以为调了。

**关闭仍然恢复打开前的快照**，不是恢复成填过的数 —— 防抖从 300 调到 250 再关掉，
设备应该回到 300。快照机制没有因为数值项而改变。

**范围只写在确认过的区间。** `_grade` 是档位不是毫秒，所以给 `0..9` 而不是毫秒范围；
响应延迟只读到过 0，不给范围、保持只读。超过预设值（防抖 300）时用户自己要为手感负责，
界面不拦，因为固件是否另有夹取没有证据。

**为什么 LEGACY 之外不该起服务**：后端是 VIVO 时根因已经被
`vivo_lcm_brightness_policy_disable` 掐掉，系统不再压暗亮度；而守卫服务做的是
"已经压暗之后把用户选的亮度放回去"，那一层纯属白烧一个前台服务加每 15 秒的轮询。
偏好仍然可以为真 —— 两种后端都叫"亮度守护开着"，只是实现不同。

顺带一条边界：**CPU 页的「释放」不停亮度守护。** 它是"守"不是"改"，
不持有任何 PowerHAL 请求，而且有常驻通知，用户看得见它在跑。
「释放」的语义见上一节。

## 加新功能的走法

### 先确定设计边界

新增功能或改变逻辑前，检查相关实现与调用方，确定职责、状态所有者、依赖方向和失败处理，
再选择沿用、扩展或拆分现有实现。简单修改直接作判断；跨模块或涉及持久状态的改动，
在任务说明中简述方案与取舍即可，长期契约变化再更新本页。

- **按职责分离变化。** 展示、业务规则、设备适配和存储各在所属边界处理；
  文案、样式和配置使用已有资源或数据定义，状态有明确的所有者。
- **以实际使用决定复用。** 先查已有能力；多处需要相同语义，或需求已明确多个用途时，
  提取共同部分。共享实现通过明确输入与结果连接调用方，功能特有的流程和保存策略由调用方负责。
  只有一个用途且变化方向不明确时，保持局部实现和清晰边界。
- **让变更局限于所属职责。** 用“增加一个同类选项、替换一种实现、移除这个功能”检查设计：
  若需要改动多处无关代码，先查是否复制了规则、混合了职责或隐藏了依赖。
  抽象应减少这些耦合；普通函数、数据定义或组合已足够时沿用简单结构。
- **验证边界行为。** 按风险检查失败、取消、重复操作、生命周期与恢复；
  可独立验证的规则和 I/O 边界便于测试。交付前同时检查功能结果、依赖关系和受影响的现有调用方。

### 接入与交付

1. 同构设置扩展 `TouchItems`、`VivoFeature` 等数据定义；不同生命周期或协议封装独立实现。
2. 沿已有控制通道接入，定义支持判断、状态和恢复行为。节点可读或命令返回成功不等于效果已验证。
3. 让新设置进入相关快照、诊断与恢复范围。`OwnedKeys.all` 是共享 settings 清单；
   prop 的漂移监测使用 `propIds`，不因此把 prop 混进 settings 备份。
4. 正式开关应有明确语义和支持依据；仍需验证的能力使用可识别的实验入口。
5. UI 表达结果和可做的操作，文案按 [wording.md](wording.md) 放入资源。
6. 按变更检查逻辑、受影响交互和必要的设备效果，完成 [文档收尾](../CONTRIBUTING.md)。

## 实验、报告与维护边界

实验自己编排步骤与采样，正式功能不依赖实验实现。需要有限时、可取消和可清理；
超时或失败时报告已经完成的步骤、释放结果与未恢复状态。

新增实验复用现有日志和输出接口。退役前检查入口注册、请求句柄、定时任务和持久恢复状态；
有未恢复的旧状态时保留恢复或迁移路径。删除实验不应破坏正式功能，必要的回归测试继续保留。

当前并非所有实验都已共用同一报告实现。接入或删除前检查实际依赖，
不把本页契约误认作全部已完成的改造。

## 日志与导出

`AppLog` 汇聚工程日志；`LogFileStore` 提供磁盘日志，
`CrashLog` 与 `DebugRecorder` 记录崩溃和诊断上下文。保留统一时间与错误链，敏感数据按输出边界处理。

`data/diag/ReportExporter` 复用适配报告与调试报告的打包、清单和存储输出。
新增报告先检查这个入口：实验负责内容，输出层负责打包、保存和分享。
导出失败应能单独重试，不必重复执行设备控制实验。备份有自己的恢复契约，不只是另一份诊断报告。

## 轮询必须有门控，且按成本定频率

**持续读取内核状态是这类应用最大的隐形开销**，而它不出现在任何一屏上，所以只能靠约定。

三条硬规矩：

1. **界面里的轮询必须随可见性停。** `LifecycleResumeEffect(isSelected)` 或
   `repeatOnLifecycle(STARTED)`，二选一，不要自己记一个布尔。
   ViewModel 比页面活得久（它挂在返回栈条目上），所以"页面不可见了"不等于
   "ViewModel 没了"—— 不门控的话，切走一个标签会让它的采样器在后台一直读。
2. **服务里的轮询必须是用户显式开着的。** 目前四个：CPU 重放（`ApplyMode=POLLING`）、
   按应用温控、高温降亮度恢复、AX 会话/任务。全都是前台服务 + 常驻通知，
   用户看得见自己开了什么。不要新增第五个没有开关的。
3. **频率按单次成本定，不按"想要多实时"。** 一次 `dumpsys activity activities`
   要几十毫秒 CPU、40 KB 输出，1 秒一次就是一小时 3600 次 —— 而它是个前台服务，
   用户在别的 App 里时也照跑。降一半频率，耗电少一半，而"切前台应用就换温控档位"
   这个用途察觉不到（游戏从点图标到开始渲染要好几秒）。
   想再降，加**屏幕状态门控**（熄屏时前台应用不可能变），而不是继续拉长间隔。

现在的轮询清单（改这个文件时同步更新）：

| 轮询 | 频率 | 门控 |
|---|---|---|
| 首页频率采样 | 1 s | `LifecycleResumeEffect(isSelected)` |
| CPU 页上限 | 2 s | `isSelected` + `repeatOnLifecycle(STARTED)` |
| 编译进度 | 3 s | 只在编译任务运行时 |
| 实验计时 | 1 s | 只在实验期间 |
| 高温降亮度 | 15 s | 用户开启；不热时只读一次设置 |
| CPU 重放 | 用户设的间隔 | 仅 `ApplyMode=POLLING` |
| 按应用温控 | 2 s | 用户开启；每轮一次 `dumpsys activity activities` |

**后期加悬浮窗/性能监视器时**：它需要实时读，所以它自己带一个门控 ——
悬浮窗显示着才采样，收起来就停。复用 `HomeViewModel.setSamplingActive` 这个入口，
不要在别处再开一条采样路径。

## 阻塞调用不许落在 Main 上

`viewModelScope` 挂在 `Dispatchers.Main.immediate` 上。**它不会因为函数带 `suspend`
就换线程** —— `PrivilegeManager.exec`、`SettingChannel.get/put`、SharedPreferences 首次读、
`File.listFiles`、`queryIntentActivities` 全是阻塞调用，`suspend` 只是让协程能让出，
线程还是主线程。

规矩：

1. **读设备、读文件、读包信息，一律 `withContext(Dispatchers.IO)`。**
   最稳的做法是包在数据层那个方法自己身上（`TweakRepository.syncSwitchStateFromDevice`
   就是），而不是指望每个调用方记得切 —— 调用方会忘，而且忘的时候没有任何症状，
   只是"这个 App 有点卡"。
2. **贵的一次读完再更新界面，不要读一项更新一次。** 跨线程传一小包不可变数据
   （见 `TweaksViewModel` 的 `SmartState`），到 Main 上一次性 `copy` 进 state。
   否则界面会看见三个中间态，白重组三遍。
3. **`_state.value` 从 IO 线程写没关系**，`MutableStateFlow` 是线程安全的；
   要躲开的是阻塞，不是状态写入本身。

> **量过的和没量过的要分开说。** 2026-10-12 那次"切标签卡一下"的排查里，
> 用 `dumpsys gfxinfo framestats` 逐帧量到的是：每次切标签固定有一帧 130 ms，
> 其中 92 ms 在主线程的 Compose 帧里。**那一帧的根因是 Pager 在动画中途第一次组合
> 邻页**（见 [ui.md](ui.md) 的 `beyondViewportPageCount`），改成常驻组合后最差帧
> 136 ms → 34 ms，是这么确认的。
>
> 本节这些主线程阻塞是**读代码读出来的，没有单独 A/B 量过**。它肯定不是零成本
> （`HomeViewModel.init` 里四次 Shizuku 往返，每次一趟 binder 加一次起进程），
> 但"修掉它到底赚回多少毫秒"没有数据。别把上面那个 130 ms 算到它头上 ——
> 那一帧每次切换都出现，而 `syncSwitchStateFromDevice` 只在 ViewModel 创建时跑一次。

## 失败结果的展示边界

失败结果分为面向用户的摘要和技术详情两层。控制层返回失败类型、可选的原始错误和上下文；
展示边界根据操作选择资源化摘要，并在失败发生的位置就近显示。摘要默认可见，说明结果，必要时给下一步；
原始异常类名、异常消息、路径、返回码和调用上下文默认收起，放入“显示更多”或信息入口，并支持复制。
不能只把详情写入日志后要求用户去日志页搜索，也不能让异常文本直接成为主提示。

复用共用的摘要/详情组件和状态模型，避免每个页面自行拼接异常字符串。日志仍保留完整错误链，
但日志可见不等于用户界面已完成错误展示；两者都需要时由同一失败结果分别供给。

### `detail` 不是可选的

**只要一条失败可能由外部原因导致（写入被拒、服务不可用、文件读不到、命令非零退出），
`Outcome.detail` 就必须有值。** 只给一个布尔或一句摘要，用户点「显示更多」时没有东西可看，
那条按钮就是骗人的。

取原始错误的三条路，按代价从低到高：

| 情况 | 怎么写 |
|---|---|
| 捕获到异常 | `Failure.from(tag, summary, e)`，构造即落日志 |
| 服务端返回错误文本 | 原样收进 `detail`（`Sysfs.writeOrNull`、`GameBoost.run` 就是这么加的） |
| 批量写，一项一判 | writer 返回 `String?`，null 表示写成；`SettingBatch` 收原话 |

`detail` 里放**设备自己说的话**（异常文本、退出码、节点路径、请求值与读回值），
不放排障建议 —— 建议是摘要的事，混在一起就退回"开发者把排障笔记搬到界面"。
`FailureNote` 只在 `detail` 非空时渲染「显示更多」，所以留空 `detail` 是诚实的，
编一句填进去才是骗人的。

批量操作还要**分开数原因**：`PrivilegeManager.exec` 返回 null 是服务没连上，
返回了但 `VivoReply.output` 为 null 是命令被拒。两者缩成同一个值时，
一次服务中断会被数成"N 处未生效"，用户照着这个数字逐项排查，什么都查不到。

### 违反过一次：把证据拼进摘要（2026-10-14 修）

`CpuControl.updateVerification` 原来返回一个 `Message`，用 `cpu_outcome_join`（`%1$s · %2$s`）
把**短结论和逐簇原始读数拼成一句**：

```
请求已发送，部分簇无法验证 · policy0 ?-?MHz cur=400MHz 请求=300-2000MHz 上下限读回不完整;
policy4 550-2400MHz cur=550MHz 请求=550-2850MHz 范围被进一步收窄; policy7 …
```

用户按一次「应用」，首页底部就横着这么三行。上面那节说的"不能让异常文本直接成为主提示"
被违反了，而**违反它的正是写出那个组件契约的同一个仓库**。

改成返回 `Verification(summary, detail)` 一对：`summary` 是那句短结论进 `message`，
逐簇读数进 `Outcome.detail`（界面默认收起，点"显示更多"才看）。

**判断标准就一句：这句话用户读完知道"成没成"了吗？** 知道 → 摘要；
它是在解释"为什么"（读回值、节点路径、异常文本）→ 详情。
`CpuControlTest` 里那条断言跟着改了：冲突原因现在断言在 `detail` 里，摘要只断言那句结论。

## 实验室的判定：自动判定撤掉，改成用户自己标（2026-10-16）

实验室原来给每项做**自动判定**：下发请求，读回判据节点，比对前后 → 生效 / 未见效 /
无法判断。还加过一个「测一遍」按钮把能自动判的项循环跑一遍。

**整套删掉了。** 因为它在这台机器上不成立：判据节点在 shell 身份下读不到
（`/dev/cpuctl/*` 是 `0660 system`、`/proc/perfmgr/**` 的 SELinux 域进不去，
见 [device/pitfalls.md](../device/pitfalls.md) 第 16b 条）。19 项里有可读节点的只有
`affected_cpus` 那一族，恰好是**会掉核**的 4 项 —— 自动判定实际能覆盖的是 **0 项**。

现在的做法：

- **两个状态由用户自己标**：`MANUAL_USABLE` / `MANUAL_UNUSABLE`，
  与自动判定**写同一张表**（`LabController.verdicts`）。两个结论分两张表，
  界面就不知道该显示哪个。
- **入口在顶栏**，铅笔图标，点进编辑模式。评分是偶尔做一次的事，
  不该让每一行常年摆着两个按钮。
- **平时列表只画一个绿勾**（标了"能用"的），"没用"的项**直接不显示**，
  未标记的正常显示。列表越用越干净。
- **编辑是一次事务**：改动先进内存草稿（`LabViewModel.pending`），
  右上角 √ 才一次性写入，左上角 × 或返回弹窗问保存还是丢弃。
  中途每点一次就落盘的话，误触没有退路。

**标记不触发重新扫描。** `mark()` 原来调 `refresh()`，而 `refresh()` 开头置
`loading = true` 把整页换成转圈 —— 每点一次闪一下、等半秒（`refresh` 要跑
`cpuScanner.scan` 和一串 shell 读），连标几项根本没法用；而草稿一重扫就被
过滤掉，× 了的项当场消失，看起来像"自动隐藏"。标记只改本地一个字段，
和设备无关，不该走重扫那条路。

**判据是体感，不是节点读数。** 这一条是这次撤换的核心：效果好不好用户说了算，
而我们能读到的节点既不全也不总对。给一个"无法判断"的自动结论，
不如让用户自己写一个他信得过的。

**写"看不见"和"不存在"要分开，写"不能判"和"不该写"也要分开。**
`LabController.apply` 因此在两处早退：节点确认不存在 → `UNSUPPORTED`（不测）；
节点读不动 → 也**不下发**（`before == null` 就返回）。后者是 2026-10-15 补的 ——
原来它会先写一次再发现读不回来，等于白白改一次设备状态换来四个字。

## 验证与交付

验证规模匹配改动：文档检查链接与冲突；UI 检查编译和受影响交互；
控制逻辑检查所有权、失败和恢复，必要时验证设备效果。桌面构建不能代替真机验证。

`python tools/check_strings.py` 检查资源引用、硬编码基线和特定文案形态；
`python tools/check_docs.py` 检查链接、锚点、总索引可达性、显式待办位置，
以及文档反引号里点名的代码标识符是否真的存在（防改名后文档不跟着改）。
判断语义仍需对照代码和证据。

每次交付新 APK 递增 `versionCode`；只改文档、仅本地测试或重新提供同一 APK 不递增。

### canary 与正式包：一个构建参数，不拆源码

未完善功能按**入口可见性**分级，不按编译裁剪。`TouchItems` / `VivoFeature` 的每一项都带
`Evidence`（`LIKELY_USELESS < WRITTEN < CONFIRMED`，声明顺序就是强弱顺序），
`BuildConfig.MIN_EVIDENCE` 是列出时要达到的最低级：

| 构建 | 默认门槛 | 效果 |
|---|---|---|
| debug（canary） | `WRITTEN` | 「预计无效」的项不列 —— 试用户不该先撞上读回成功但本机没反应的开关 |
| release | `LIKELY_USELESS` | 全部可见，靠 Evidence 标签说明 |

`-PminEvidence=` 可覆盖两者（例如发一个只含已确认项的验证包）。判定在 `TweaksViewModel.touchItemsById`。
参数写错（不是合法枚举名）时列表照旧全显示，不因为一个构建参数变空。

**为什么不用 flavor / 把文件挪到 `src/stableMain`**：Kotlin 的 `src/main` 对所有产物都编译，
要做到"代码不进包"只能搬文件，而每个被搬走的文件都要连带改 import、`AppContainer` 接线和
导航入口，同一份特性随后要在两个目录各维护一份。而"这个功能成不成立"本来就随机型变化 ——
同一份代码换台 MTK 机就可能有用。所以裁剪的收益不在体积，而在**产品承诺**。
