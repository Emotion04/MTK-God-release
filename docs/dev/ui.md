# 界面指南

本页记录共享交互契约；组件参数和功能清单查源码。文案规则见 [wording.md](wording.md)。

## 导航与页面状态

当前底栏为“首页、性能、工具、设置”，定义在 `ui/navigation/Destinations.kt`，
路由和返回行为在 `AppNavHost`。方案属于性能功能，不是独立底栏目的地。
设置分类使用分类参数路由，新增同构分类复用现有入口。

顶层横向切页使用 `TabsPager`，子页使用导航栈。返回子页时保留顶层选中项和编辑状态。
`TabsPager` 忽略首次 `settledPage` 发射，避免它把外部保存的选中项误判为用户滑动。

### 底栏切换：两种手势同一套逻辑

切标签有三条路 —— 点底栏、左右滑页面、拖着底栏滑。**三条都走
`AppNavHost.switchTab()`**，所以行为不可能分叉。曾经滑动只改选中项、不收记忆也不还原，
于是"滑走再滑回来"丢位置，而点一下却不会：同一个动作两种结果。

**落到哪儿完全由 `TabRestoreMode` 决定，与用哪根手指无关：**

| 模式 | 切到某个标签 |
|---|---|
| 保留（`KEEP`） | 还原那个标签上次停住的**整条**子页链；没有就落主页 |
| 重置（`RESET`） | 一律回标签主页 |

保留模式下点**当前**标签是空操作 —— 你要的"上次那一页"就是眼前这一页；
想回这个标签的主页用系统返回键，那同时也表示"我退出了这一层"，记忆按同一条规则作废。
重置模式下点当前标签则回主页：那一档的语义就是"切就回主页"，否则从深层子页出来
只剩系统返回键一条路。

三条必须守住的约定：

- **记忆的是链，不是一页。** `settings/lab` → `settings/lab/panel` 是两层；
  只记最上面那层，还原后按返回会从 panel 直接跳回 `tabs`，中间一层被吞掉。
- **记忆的键是"离开时的那个标签"，不是路由前缀。** 从工具页钻进去的
  `settings/notifications` 前缀属于设置，按前缀分会记到设置名下，位置就丢了。
  底栏高亮也用同一个来源 —— 子页是压在**当前标签**之上的，不是另一个标签。
- **保存和读取用同一个条件。** 只在保存处判 KEEP 的话，用户先在 KEEP 下设了记忆、
  再切成 RESET，旧条目还躺着，点标签会把旧二级页还原出来，与 RESET 的承诺相反。

栈的数据取自 `navController.currentBackStack`，不自己攒 —— 自己攒要和系统还原、
返回键、屏幕内部发起的 `navigate` 三方保持一致，漏一个方向就和真实栈分叉。
`TabsPager` 的 `settledPage` 收集器要经 `rememberUpdatedState` 取回调：那个
`LaunchedEffect` 的 key 只有 `pagerState`，重组不重启它，否则协程里一直是旧 lambda
—— 里面算出来的普通 `val` 全是第一次组合时的值。

**滑动松手那一刀必须自己调 `switchTab()`，不能只滑 Pager。** 曾经 `onSettle` 里只有
`animateScrollToPage()`，指望 Pager 停住后由 `settledPage` 回调 `onTabChange` 来切。
但二级/三级页压在 `TabsPager` 之上时，`TabsPager` 根本没被组合，那个收集器没在跑 ——
于是 `selectedTab` 和导航栈都不更新：胶囊跟着滑过去了，页面还停在原地。
点击走 `onSelect → switchTab` 所以一直是好的，滑动这条路漏了它，两条手势就此分叉。

**归位必须无条件做。** 曾经判 `destination == selectedTab` 才归位，理由是"变了他会滑"，
而那个"他"是 `TabsPager` 里 `currentPage != selectedIndex` 这个 guard —— 它恰恰会漏：
**拖过中线松手时 Pager 的 `currentPage` 已经跳到目标页**，guard 判等成立，归位动画被整段
跳过，页面停在两页中间，用户要再碰一下才好。所以 `TabsPager` 的 guard 必须同时看页码和
偏移：`currentPage == selectedIndex && currentPageOffsetFraction == 0f` 才算真的到位。

`onSettle` 里归位是**有条件**的：只有标签没变时才自己滑。标签变了的话
`selectedTab` 一变，`TabsPager` 那个 `LaunchedEffect(selectedIndex)` 就会滑过去，
这里再滑一次是重复劳动。这个分工成立的前提就是上面那个 guard 是对的 ——
两边判"到位"必须是同一个条件，否则一定有一边漏。

页面可见性与生命周期共同控制采样；预加载页面也要通过 `isSelected` 门控设备工作。
动画持续时间取共享 Motion 配置。

### 标签层必须常驻，而且必须在 NavHost 外面

两条，都是实测出来的，缺一条就卡：

**一、`HorizontalPager` 的 `beyondViewportPageCount` 给页数减一，四个标签全部常驻组合。**
Pager 按"离当前滚动位置多远"决定组合哪些页，滑动一开始边界就往外扩一页，那一页此刻才
第一次组合。实测每一跳都有**一帧**卡在 130 ms，其中 92 ms 在主线程的 Compose 帧里，
而它落在动画中段 —— 用户说的是"点一下卡一下"，跨两页的切换要连造两页，掉帧更多。
常驻之后切换是纯动画，没有组合也没有布局。冷启动那一帧仍然只造当前标签，
`withFrameNanos` 等一帧再补齐，别把另外三个塞进用户等得最久的那一帧。

**二、标签层渲染在 NavHost 之外，`composable(TABS_ROUTE)` 是空的。**
放进 `composable(TABS_ROUTE)` 的话，一进二级页它就离开组合、返回时整套重新组合加重新
布局。实测返回一帧要 233 ms，其中 228 ms 全在 measure/layout/draw 上 —— 用户说的是
"按了返回要停半秒动画才开始"。挪到外面之后标签层永不销毁，进出子页只剩子页自己那一层
过渡：返回最差帧 300 ms → 38 ms。

两个必须一起做的配套：

- **ViewModel 作用域要显式指回去。** 挪到 NavHost 外面之后 `viewModel()` 取不到
  NavBackStackEntry，会一路落到 Activity 上；而「高级设置」二级页要复用的正是标签那一份
  `CpuViewModel`。所以用 `CompositionLocalProvider(LocalViewModelStoreOwner provides …)`
  把 `TABS_ROUTE` 条目指回去，标签层拿到的和以前完全是同一个 store。
- **`TABS_ROUTE` 空着是有意的。** 不空的话那一层会盖住标签、把触摸吃掉。NavHost 全栈
  没有任何 `pointerInput` 节点，所以空目的地上触摸会穿过去落到标签上；子页压着时子页
  自己有滚动手势，触摸自然归它。

代价是四个标签的界面同时活着，所以**周期读取必须按 `isSelected` 门控**
（见 [architecture.md](architecture.md) 的轮询一节）：没选中的那一页只是"组合着"，
不读任何节点、不发任何请求。

内存上这笔账是这么记的：标签层只在 NavHost 里时装当前页时，冷启动静置后
`dumpsys meminfo` 的 TOTAL PSS 在 145 MB 上下；改成常驻之后同一测法落在 185 MB 左右。
**这两个数不是同一次对照实验量出来的**（中间还隔着一轮别的改动），只当数量级看：
四个标签的界面常驻大约值几十兆，换的是主交互不掉帧。真要抠这个数，
得把 `beyondViewportPageCount` 单独 A/B 一轮。

底栏避让读 `LocalNavBarClearance`；子页按 `SubScreenScaffold` 的布局处理，
由共享布局统一避让。留白随 `NavBarVisibility` 的固定或自动隐藏模式变化，页面使用该值。

## 共享组件

按信息关系选择组件，具体样式由 `ui/components/` 定义。

| 场景 | 组件 |
|---|---|
| 设置项及说明、开关或值 | `SettingsRow`、`SettingsCard` |
| 分组标题和分隔 | `SectionLabel`、`InsetDivider`、`InfoHeading` |
| 简短状态 | `StatusChip`、`StatusTone` |
| 功能解释与授权状态 | `FeatureInfo`、`ShizukuStatusCard` |
| 可排序列表 | `ReorderableColumn` |
| 方案标签 | `ProfileTagRow` |

短确认适合弹窗；需要比较、滚动阅读或持续观察的内容使用详情区域或页面。
状态摘要先给结果和可做的操作，原始字段与详细错误放到可展开的诊断区域。
诊断本身可以显示路径、协议标识和设备原文；普通控件标题用用户能理解的名称。

### 选项状态

选项由主标题、操作和可选的尾部状态组成；主标题保持一行，状态使用 `StatusChip` 等独立元素。
状态标签保持简短，和用户要作的决定处于同一信息层级；不能确定效果时表达不确定性，
确认能力缺失时表达不可用。颜色与图标辅助文字，并提供无障碍语义。

主控件展示结果和下一步，探测路径、返回码和内部标识符进入详情或诊断区域。

长任务在操作附近显示进度或经过时间、最终结果和恢复状态。
停止采样与释放控制分别呈现；仍未知的效果不能显示为已生效。

## 主题与布局

使用 `MaterialTheme` 和现有 Palettes、Shapes、Motion；
状态色取共享状态 token（如 `LocalStatusOk`），形状取 `LocalShapeStyle`，
动效取 `LocalMotion`。避免页面复制一组主题颜色和组件尺寸。

`Surface` 的背景与内容色成对选取：**页面根部用 `Surface(color = background, contentColor = onBackground)`。**
不是形式要求 —— 不给 `contentColor` 时 Compose 的默认 `LocalContentColor` 会让深色主题里
那些没有显式指定颜色的文本**变成黑色**。

控件随文字缩放和可用宽度布局，图标按钮保留触控与无障碍语义。
已有页面整体调整时检查浅色、深色和长文本。

排序列表使用稳定 key。拖拽结束动画从实际落点过渡到目标，
变高条目不能假设统一高度或从零偏移开始动画。

## 卡片内的文字与间距

**`SettingsCard` 本身不加水平内边距，行组件自己负责。** 卡内一律用
`SettingsRow`（自带 16dp）或 `SettingsRow` + `trailing = { Switch(...) }`；
无图标的开关行用 `SettingsSwitchRow`。
`ToggleRow` **不自带内边距**，只用于已经有 16dp 的 `ToolCard` 一类容器；
把它直接放进 `SettingsCard` 会贴到卡片左缘。新增设置项按这个分工选组件，
不要在调用点各自补 `padding(start = 16.dp)`。

### 设置的两级分类

**一级按“用户想改哪类东西”分，不按数据存在哪个类里分。**

| 一级 | 放什么 |
|---|---|
| 通用 | App 自身：启动标签、最近任务、标签交互、后台白名单 |
| 外观 | 主题、主题色、圆角、动画、底栏 |
| 性能 | CPU 下发、控制页、触控与显示、厂商性能档 |
| 通知 | 常驻通知、显示内容、系统通知设置 |
| 实验室 | 实验入口、按应用温控、逐 ID 测试、归档 |
| 维护与诊断 | 诊断、日志、导出报告 |
| 备份与恢复 | 方案与偏好的导出、导入 |

**二级页用“灰字分组标题 + `SettingsCard`”组织**：每个分组先 `SectionLabel`，
再一张或多张卡片；组内按“常用在上、危险/排错在下”排序。同一页的分组不重复
一级标题里的词 —— 例如“性能 → CPU 下发”里的行叫“应用方式”“锁屏时”，
不再写“CPU 应用方式”。新增设置项先归组，再选行组件，不直接往页面底部追加。

### 2026-10-22 确认的设置结构（后续按此维护）

| 一级 | 二级分组（从上到下） |
|---|---|
| 通用 | 启动与任务 → 交互 → 后台与电池 |
| 外观 | 主题 → 底栏 |
| 性能 | CPU 下发 → 控制页 → 触控与显示 → 厂商性能档 |
| 通知 | 常驻通知 → 通知外观 → 显示内容 → 系统设置 |
| 实验室 | 实验入口 |
| 维护与诊断 | 诊断与日志 |
| 备份与恢复 | 配置备份 |

一级页保留：Shizuku 授权卡、分类入口、恢复默认、关于。二级页不重复一级标题；
每页第一个分组是用户最常改的，排错/清空类放最后。所有卡片内的行统一左对齐到
16dp（`SettingsRow` / `SettingsSwitchRow` 自带），不再出现某个新增行贴边的情况。

**标题组件只用于标题。** `InfoHeading` 的标题位没有左内边距，且带标题排版
（`titleMedium`）和一个信息按钮。把**状态行、数值、读数**塞进去，一次错三处：
文字贴到卡片左缘、一行数据占了标题的层级、还多出一个文不对题的信息按钮。

> 实例：导出诊断页的「日志占用 2 MB，上限 160 MB」曾被写进 `InfoHeading` 的
> title 位，于是贴着卡片边缘。它是状态行，改成带 16dp 内边距的普通 `Text`。
>
> 这次两条都没守住：规范没写「标题组件只用于标题」，而 `ui.md` 里也早有一条
> 「状态摘要先给结果和可做的操作」——那句话讲的是内容，不是排版位置。
> 现在这条补上，并且把判据写成可检查的：**一段文字是不是标题，看它会不会变。**
> 会随设备状态变的（占用、读数、版本号）就不是标题。

同类判据：`SettingsRow` 的 `subtitle` 是给"这一行是什么"的说明，
不是给动态读数的；动态值走 `trailingText` 或 `trailing`。

## 按钮与操作

**多个按钮不要强制等分宽度。** `Modifier.weight(1f)` 均分时，最长的那颗必然在
词中间折行（「保存到文 / 件」），第二行只剩一两个字。改用 `FlowRow`：
按钮按内容宽度排，排不下整颗换到下一行，**文字永远不拆**。

**不要用缩小字号来避免折行。** 那会让这一屏的按钮和别处字号不一致，读起来更累，
也伤无障碍。按钮文字长就改标签，或者让它换行成整颗。

**一屏一个实心按钮。** 主操作用 `Button`（主题色），备选用 `FilledTonalButton`，
再退一级才用 `TextButton`。三个出口并列时，只有"最可能被点的那一个"上主题色。

## 结果的呈现形式

**一次操作的结果跟着产生它的内容走，用行内文字。** 不因为"想醒目"就换成 Toast 或
Snackbar —— 行内文字不消失，而且「显示更多」需要一个**驻留的锚点**，Toast 一闪就没了，
用户点不到。

| 形式 | 用它做什么 | 不要用它做什么 |
|---|---|---|
| 行内（`FailureNote` / 普通 `Text`） | 成功与失败的结论、可展开的原始错误 | —— |
| 底部浮条 | 一次性确认，且用户接着就要离开当前页 | 任何需要用户读完之后做判断的事 |
| `Toast` | 只在系统表面（状态栏快捷开关）没有行内锚点时用 | 页面内的任何结果 |

设置项改完不需要任何提示 —— 行内那一个控件显示的就是结果，顶栏副标题、
`trailingText`、开关本身就是反馈。**只有离开页面就看不到结果时才值得用底部浮条**，
例如「导出完成后跳到了系统文件选择器」。

### 成功提示要共用

「已保存」「完成」这类**一次性成功结果**放共用的 `result_*` key，不要在页面里各写一份。
同一个意思散在五处，改一处漏四处。

### 失败必须能看见原始错误

**只要一条失败可能由外部原因导致，`Outcome.detail` 就必须有值。** 只给一个布尔或一句摘要，
用户点「显示更多」时没有东西可看，那条按钮就是骗人的。`FailureNote` 也只在 `detail` 非空时
渲染那颗按钮 —— 所以留空是诚实的，编一句填进去才是骗人的。

取原始错误的几条路、`detail` 里该放什么不该放什么，见
[architecture.md](architecture.md#失败结果的展示边界) 的「`detail` 不是可选的」。
这里只记界面侧的两条：

- 摘要只说结果，**不要编一套排障建议**（见 [wording.md](wording.md#报错分两层不许合成一句)）
- 批量失败要能**分开数原因**：服务没连上和命令被拒是两件事，缩成一个数字会让用户照着
  "N 处未生效"逐项排查，而那儿什么都没有

## 功能编辑

CPU 编辑区区分草稿、保存方案与真正下发。校验上下限关系，
保留独立控制和原有恢复语义；切换标签不能悄悄提交或丢弃草稿。

### 频率区间控件契约

分段条是**离散频点选择器**，不是连续 Slider —— 每格对应 `availableFreqs` 里一个频点。

| 手势 | 状态变化 | 何时写设备 |
|---|---|---|
| 单击一格 | 锁到该频点 | **不写**，等「应用」 |
| 再单击另一格 | 取两格之间的区间 | **不写**，等「应用」 |
| 水平拖动 | 取拖过的区间 | **不写**，等「应用」 |
| 拖动取消 | 回到提交前的状态 | 否 |

**拖动中的高亮是预览态，不碰持久化设置。** 组件的唯一输出是 `onRange(index, lo, hi)`，
调用方还要再归一化一次 —— 上下限**只能由值的大小决定**，不能按"先点左边"或"手指朝哪边拖"
来定，否则同一个区间从左右两个方向操作会得到相反的结果。

设置里可以把这一栏换成双向指针条（`RangeControlMode`）：外观和产出都相同，只是手势模型不同。
GPU 选项依据实际能力与取值表展示，未知读数与零值分开。

**弃用过的是「双滑块」这一个类，不是 `Slider` 本身。** 频率区间需要的是「离散频点」，
每格对应 `availableFreqs` 里一个真实频点，双向指针给不出这件事 —— 所以那一处不用
`RangeSlider`。别把它读成「项目不用 Slider」：连续值（色相、浓度、间隔）用 `Slider` 是对的。
自定义主题色的两个滑杆就是这么用的。

**数值项用滑杆加输入框。** 触控里按下防抖、指针速度这类背后是数的项，
每个键一条滑杆加一个框：滑杆粗调（手感驱动、边拖边试），框精调（知道自己要哪个数）。
框下写明可填范围，旁边一行「设备现在：X」—— 与框里的数不同就说明还没写进去。
框里不是合法数时滑杆停在上一个有效值；同一个旋钮的现有值合成一行列出，不一个键占一行；超出范围时不写、标红、保留原输入，不悄悄夹取成边界值。

温控策略的档位说明**以 CPU 高级页为准**，实验室复用同一个 `ThermalPolicyOverview`，
不另写一套纯文字摘要。一个档位显示两种互补的图：

- **阶梯矩阵表**（`ThermalLadderTable`，heatmap table）：行是温度、列是核簇，
  每格是频率条 + 精确值，用来横向比较同一温度下三簇各被压到多少；
- **阶梯折线图**（`ThermalLadderChart`）：横轴温度、纵轴频率，每簇一条线。
  配置是阶梯函数，所以画水平段 + 垂直跳变，**不做平滑曲线**（平滑会插出不存在的频率）。
  拖动/点击曲线会吸附到最近配置温度，显示该温度下三簇的具体上限与各自物理上限的百分比，并高亮表格对应行。
  纵轴顶端取超大核物理上限，上下左右留出余量；图例可点击隐藏曲线，重合时用实线/长虚线/短虚线区分。

GPU 频率、充电限流用两列小表（温度 / 数值），不再用 `→` 串成一句话。
三处都现读现解设备上的配置，代码里没有"索引 → 含义"的固定文案表，
所以某档在另一个 ROM 上的含义与这里不同时，说明跟着变而不是说谎。
读取或解析失败时说明失败；
“某配置没有 CPU 限频表”只描述该配置，不等于全部温控机制已关闭。
传感器原始名称可以用于诊断，不凭名称推定其物理位置。

## 适配测试

维护与诊断 → 诊断导出页顶部有「适配测试」：

1. 点「开始适配测试」；
2. 去 CPU 页或实验室复现问题；
3. 回来点「结束并生成报告」，自动生成一份包含本次窗口日志、设备快照和
   CPU 请求状态的 zip，可直接分享/保存。

「允许无回读下发」只在会话期间生效：判据节点读不到时，CPU 频率资源仍可做
**5 秒有界下发**，结果记为未知，由用户体感或报告判断。

**会话状态比诊断页活得久。** 点开始后可以离开页面去 CPU/实验室复现，回来仍显示
“结束”；只有点结束或进程退出才关闭。原来状态挂在 `ExportViewModel` 上，返回
诊断页时页面被弹出、ViewModel 被清掉，会话就丢成“开始”了。

## 更新日志

入口是**关于页的版本号本身**（`v0.5.1 Canary`），不再单开一行。

页面是只读时间轴：左侧竖线与版本节点，版本号用低饱和橄榄绿，日期灰字跟随；
版本标题下可有一句摘要。条目按类型归组，**每种标签在一个版本里只出现一次**，
下面跟多条内容；标签用中文小徽章（新增 / 修复 / 优化 / 杂项），浅色和深色各有
一套底色、文字色和同色系描边。条目之间是 0.5dp 极细实线，颜色浅到隐约可见。

每次进入页面拉一次远端 JSON；主地址失败试备用地址，都失败才用 APK 内置的那份，
并在顶部说明来源。不缓存到磁盘、不轮询。条目只做纯文本，不解析 Markdown，
避免远端内容控制界面样式。

## 关于页与检查更新

关于页底部：版本号 chip（`v0.5.1 Canary`，点开更新日志）→ 联系人几行 →
「检查更新」行（图标 + 标题 + 结果副标题，检查中右侧转圈）→ `versionCode N` 一行。
**不显示包名**：那是内部标识，对用户没有信息量。

检查更新的结果统一走同一个弹窗（启动自动检查与手动检查共用，见 `UpdateCenterDialog`）：

- 标题「发现新版本」，正文第一行是新版本号 + `版本号 N`，第二行是当前版本（有包体大小时附带）；
- 更新日志一段，最长 220dp 可滚动；
- 有直链（`.apk`）且清单给了 `size`：主按钮「下载」→ 显示进度条与「已下载 / 总共」→ 完成后
  变成「安装」（跳系统安装器；未授权时先跳本应用的「安装未知应用」设置）；
- 没有直链或没有 `size`：主按钮「前往下载」，打开下载页，不在应用内猜测进度；
- 「稍后」关掉并记住该版本；强制更新（低于 `minVersionCode`）时不显示「稍后」。
- 下载失败只显示一句原因，按钮恢复为「下载」。

## 通知与常驻服务

**常驻通知就是设置里的「通知」开关本身，不再额外发一条通知。** 设置 → 通知 页打开它，
这条通知出现；关掉它，一起消失。

通知内容只保留一行：**当前方案名 + 各簇频率上限 + 电池温度**，例如
`日常 1.8/2.8/3.0 31℃`。不加“CPU”“电池”等标签，不把逐簇读数铺成多行。
读不到的值直接省略，不用占位符。

- 点击系统 App 图标或文字以外的通知区域：打开 App。
- 点击文字区域：等同于「应用 / 释放」——有请求时释放，没有请求时按上一次范围应用。
- 文字只有一行：模式名在前，频率和温度跟在后面，模式名不做加粗标题。
- 操作按钮：`下一方案`、`应用/释放`、`结束`。
- 任何通知操作完成后弹 Toast；通知本身只更新状态。

## 锁屏联动与快捷开关

设置 → 性能 → CPU 下发 → 「锁屏时」三档：不处理 / 保持并重发 / 释放并重发。默认保持。
两档联动都在亮屏后重新下发一次；释放档只在熄屏期间撤掉频率请求。
**锁屏联动不开前台服务、不发通知** —— 它在 App 进程里注册屏幕广播；进程被回收后
不再生效，需要跨进程死亡保持时由「通知」把进程留住。
这里只管 CPU 频率，温控、实验室和 GPU 不跟着释放。

同一卡片还有「开机后自动应用」：默认关；开启后开机广播启动一次后台服务，
等 Shizuku 就绪再按上一次范围下发，5 分钟等不到就放弃。

状态栏快捷开关的标签是应用名「MTK God」。开关状态按**当前有没有活动频率请求**
显示，`onClick` 才写：有请求就释放，没有就按 `lastRequested` 恢复。下拉状态栏、
`onStartListening` 只读，不做任何下发 —— 否则每次展开面板都会和厂商 boost 抢写。

设置 → 通用 → 「隐藏最近任务卡片」用 `ActivityManager.AppTask.setExcludeFromRecents`，
只改本应用自己的任务，不改系统设置；失败只记日志，不影响使用。每次回到前台重新应用，
保证新建的任务也带上标记。

## 修改页面时的检查

对照现有状态模型确认保留了数据、操作、独立选项、只读与实验标识，
以及进度、错误和恢复结果。按实际改动检查返回、滑动、拖拽、输入和导出。

`check_strings.py` 的形态扫描只能发现部分问题；信息是否清楚、支持判断是否准确，
需要结合 [设备事实](../device/facts.md) 和具体交互判断。
